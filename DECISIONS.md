## D-31 — Accelerator selection is a runtime concern (amends D-02)
- Status: Accepted (2026-10-12) · Type: Revision R1
- Context: The same binary has to run everywhere — KVM workstations, Macs, Windows laptops (Home included), with or without hardware acceleration.
- Decision: **Accelerator selection is a runtime concern, never a build-time one** (amends D-02). `internal/vm/accel.go` checks the hardware option for the host OS and returns the first usable one: Linux — `/dev/kvm` exists and opens read-write → `kvm`; Windows — WHPX available (`WHvGetCapability(WHvCapabilityCodeHypervisorPresent)` from `WinHvPlatform.dll`, confirmed by a short QEMU probe launch whose stderr is inspected on failure) → `whpx`; macOS — `kern.hv_support` = 1 → `hvf`; otherwise `tcg` (pure software emulation, always works). QEMU gets `-enable-kvm`, `-accel whpx`, `-accel hvf` or `-accel tcg`. If a hardware accelerator fails at launch, QEMU is relaunched **once** with `tcg` and the fallback is shown in the terminal, the viewer and the audit log (§7.9). The host binary stays `CGO_ENABLED=0`: Windows APIs go through `golang.org/x/sys/windows` lazy DLL calls, and TCG is only a QEMU flag.
- Consequences: — (see Decision)
- Supersedes / superseded by: amends D-02

## D-32 — --accel and --slow flags
- Status: Accepted (2026-10-12) · Type: Revision R1 · **Interpretation**
- Context: The brief named `--slow` without defining it; this reading makes it the explicit "no hardware acceleration" switch.
- Decision: Flags: `--accel` = `auto` (default), `kvm`, `whpx`, `hvf` or `tcg`, plus `--slow`. An explicit value must match the host OS (kvm on Linux, whpx on Windows, hvf on macOS; otherwise a usage error), skips detection, and still gets the single TCG retry. `--slow` is shorthand for `--accel=tcg` — deliberately run without hardware acceleration (troubleshooting, broken WHPX); combining it with `kvm`, `whpx` or `hvf` is a usage error. Whenever the effective accelerator is `tcg` (chosen, forced or fallback), VM-layer timeouts (launch window, boot-to-agent wait, agent push and handshake) are multiplied by 4; safety budgets, LLM timeouts and agent tool timeouts do not change.
- Consequences: — (see Decision)

## D-38 — Phase 1 CLI and configuration rules the plan left open
- Status: Accepted (2026-10-12) · Type: Interpretation
- Context: PLAN.md P1-T02…T05 list flags, precedence and exit codes but not several edge rules that a safety tool has to settle one way or the other.
- Decision:
  1. **`--unsafe` is flag-only.** It is not a config key and is rejected in the config file and in `CONTROLSNACK_SAFETY_UNSAFE`, so nothing outside the command line can silently relax the safety layer for every later run (extends D-17).
  2. **Limits can be tightened freely; loosening them needs `--unsafe`.** The defaults of Appendix C are the safe maxima (2 actions/s, 3 per response, 60 per task, 100 turns, 60 min). Under `--unsafe` the maxima become the §6.2 values (10, 10, 500, 500, 8 h). Values outside the applicable range are usage errors that name the flag.
  3. **`--viewer none` needs `--unsafe` unless `--no-llm`** (D-20). A non-loopback `--base-url` must be `https` unless `--unsafe` (D-08). A `--base-url` needs an explicit `--llm` so the protocol is known; URLs with credentials are refused.
  4. **`--vm` (resume a kept VM) and `--keep-vm` (create one) are mutually exclusive.** `--keep-vm` without a value means a generated name (`auto`); a name must be written `--keep-vm=NAME`. `--no-llm` conflicts with `--task`.
  5. **`--allow-domain` / `--allow-port` typed without `--allow-net` is a usage error;** the same keys coming from a file or the environment only produce a warning. `net.allow_ports` are ports *in addition to* 80 and 443. `net.deny_domains` is config-file only.
  6. **The environment layer is read through an injectable `Getenv`** and merged above the file and below the flags; an empty variable counts as unset. Unknown keys in the config file are errors (typos must not be silently ignored).
  7. **`kill`, `version`, `schema`, `--help` and the bare command never read the config file** so a broken file cannot block the emergency stop or the help. `config show` prints first and validates after, so the values that are wrong can be seen. `doctor` accepts `--accel`, `--slow` and `--qemu` so the verdict can be checked for a forced setting (extends D-32).
  8. **Exit code 5 covers interruption** (Ctrl+C/SIGTERM/SIGHUP, a canceled context) as well as the kill switch. A second signal ends the process immediately.
  9. A tiny leaf package `internal/exitcode` holds the codes and `ErrNotImplemented` so every layer can return a coded error without importing the CLI; each package that owns a command's behavior defines the service interface the command calls, with a placeholder that exits 70 and names the task that replaces it.
- Consequences: PLAN.md §4.1 gains `internal/exitcode`; `internal/cli` groups some small commands per file instead of strictly one file per command.
- Supersedes / superseded by: extends D-17, D-20, D-32

## D-39 — Exec policy: scope, invariant rules and what is deliberately not analyzed
- Status: Accepted (2026-10-12) · Type: Interpretation (PLAN.md §6.3, §6.4, P2-T02, P2-T03)
- Context: the plan fixes the engine's behavior but leaves open which default rules a user policy may relax, how far wrappers and scripts are followed, and what happens with inputs that could make the analyzer itself a target.
- Decision:
  1. **Invariant rules** (a user policy can neither change nor disable them): DENY-UNPARSEABLE, DENY-DYNAMIC-CMD, DENY-NOT-ALLOWLISTED, DENY-PIPE-TO-SHELL (they keep the analysis sound: what cannot be read is not run) and DENY-PRIV-ESC, DENY-FIREWALL, DENY-KERNEL, DENY-RAW-DEV-WRITE (they defend the guest's own isolation layers, D-21). The rules that only protect a disposable guest (ROOT-WIPE, DISK, POWER, ACCOUNTS, MASS-KILL, FORK-BOMB, and every CONFIRM rule) can be relaxed with `override`.
  2. **Every command is found by walking the whole AST** (syntax.Walk), so nesting cannot hide one; context (pipe position, background, redirects) comes from the ancestor stack. Wrappers are peeled and each layer is also judged (`sudo rm -rf /` hits both). Followed: `bash -c`, here-documents and here-strings, `trap`, `find -exec` (with `{}` replaced by the start paths and `rm` treated as recursive), `watch`, `flock -c`, `source`, script files via the ScriptReader hook, and scripts written earlier in the same action when their content is known (`cat > f` with a literal here-document, plain `echo`).
  3. **Refused rather than guessed:** unparseable input, a command name from an expansion or containing a glob, nesting beyond 3, a script written and run in one action with unknown content (printf, echo -e, curl -o, cp, tee ...), more than 4000 commands or 12 scripts in one action, brace expansions above 256 words (a `{a,b}{a,b}...` memory bomb), a script the ScriptReader cannot read or that exceeds 64 KiB. Any panic inside the analysis is recovered and becomes DENY-UNPARSEABLE.
  4. **Not analyzed (documented limitation):** the code of other interpreters (python, node, perl, awk's system(), vim...), compiled programs, and arguments whose value is only known at run time (they are allowed; a recursive delete of one is a confirmation). The exec policy is a guardrail; the VM is the boundary (D-16).
  5. Rules are data (`default.yaml`, a small match DSL plus named Go detectors); user policies get strict parsing, IDs prefixed USER-/CONFIRM-REGEX-/DENY-REGEX-, RE2 regexes only, and a content hash for the audit log.
- Consequences: the rule list in §6.4 gained engine-raised IDs (DENY-UNPARSEABLE, DENY-NOT-ALLOWLISTED) and the GUI rules of D-40.

## D-41 — Audit chain, kill switch and session lock details
- Status: Accepted (2026-10-12) · Type: Interpretation (PLAN.md §5.5, §5.6, §6.8, §6.9, P2-T07, P2-T08)
- Decision:
  1. **Audit.** One file per session, created O_EXCL, mode 0600, fsync per record, sticky write error (the session must stop when the trail cannot be written). A line must equal the canonical marshaling of the record it decodes to, so adding, reordering or re-spacing fields is detected. Truncation at a record boundary leaves a valid chain; it shows as "no end record", and `Report.LastHash` can be stored elsewhere to anchor the log. The chain is tamper-evident against edits, not authenticated against an attacker who recomputes it (no key is kept from the same-user adversary).

  3. **Lock.** `active.json` is created with full content by hard-linking a temp file (atomic, exclusive); a process is recognized by PID **and** start time (/proc stat on Linux, sysctl on macOS, GetProcessTimes on Windows), so PID reuse never gets an innocent process killed. A corrupt lock is reported, never deleted. `controlsnack kill` sends the bearer token only to a loopback IP literal over http; without an acknowledgement within 1 s it ends QEMU and then the controller directly (verified by start time) and removes the lock.
  4. Interfaces changed from the Phase 1 placeholders: `Killer.Kill(ctx, w)` and `audit.Admin.Show(..., raw bool)` (`audit show --raw`).

## D-43 — QEMU discovery rules
- Status: Accepted (2026-10-12) · Type: Interpretation
- Context: PLAN §7.1 gives the search order and "qemu-img must sit alongside"; it leaves open what an explicit choice that fails does, how PATH is read, and how features are probed.
- Decision:
  1. **An explicit `--qemu` / `vm.qemu_dir` is never replaced.** If it is missing or lacks either program, discovery fails naming that one place; it does not fall back to PATH. A path to one of the programs means its directory.
  2. **Only absolute PATH entries are searched.** `.`, `bin` and empty entries are skipped: the result must not depend on the directory `controlsnack` is started in, and a planted `qemu-system-*` in a working directory must not be picked up. Duplicates are tried once.
  3. **Both programs in one directory, regular files, executable** (the `.exe` extension decides on Windows; symlinks are followed, as Homebrew needs). Each place tried is kept with its reason, so `doctor` and the error message can say why.
  4. **Features are asked, not inferred** (D-02): minimum major version 8, then `-accel help`, `-machine help` and `-device help` are parsed (aliases count as device names) and every machine and device the runtime argv names must exist; the `Install` is returned together with a `*VersionError` / `*FeatureError` so `doctor` can still show it. A too-old QEMU is not asked further questions.
  5. **`-sandbox` is probed once, on Linux only**, by starting an empty machine (`-machine none -S -qmp stdio`) under `SandboxArg` and sending `qmp_capabilities` and `quit` on stdin. The quit is required: measured with QEMU 8.2.2, a QMP session whose stdin ends does not exit. Exit 0 means supported; the argv builder adds the option only then.
  6. **aarch64 firmware** is searched next to the installation (`../share/qemu`, `../share`, `share`, also behind symlinks) and then in the standard system directories, for four known file-name pairs (QEMU's own, Debian AAVMF, Fedora, Arch). Both files of a pair must exist. x86_64 uses the BIOS inside QEMU and needs none. Missing firmware is not a discovery error; `Install.RequireFirmware` explains what to install when an aarch64 run needs it.
  7. Probe programs run with a minimal environment (`PATH`, `HOME`, Windows system variables, `LC_ALL=C`), output capped at 512 KiB, 30 s each. The guest architecture defaults to the host's: the guest is never emulated across architectures.

## D-46 — QEMU process supervisor
- Status: Accepted (2026-10-12) · Type: Interpretation
- Context: PLAN §7.4 lists the per-OS mechanisms for tying QEMU to the controller; details such as which pid is killed under the macOS reaper, and the Go runtime's thread behavior with `Pdeathsig`, are not specified.
- Decision:
  1. `qemu.Start(ctx, argv, opts)` returns a `*Process` that satisfies `killswitch.QEMU` (`Kill`, `Exited`). `argv[0]` must be an absolute path (a name resolved through PATH is refused). Minimal environment (`PATH`, `HOME`, Windows system variables, `LC_ALL=C`), cwd = the session directory, stdout and stderr merged into a 64 KiB `Ring`. Cancelling `ctx` kills the whole process group; the kill switch kills first and cancels afterwards, so this is a second line.
  2. **Linux:** own process group (`Setpgid`, so Ctrl+C aimed at the controller does not reach QEMU, which the controller then stops through the kill switch) and `Pdeathsig: SIGKILL`. The kernel delivers `Pdeathsig` when the *thread* that created the child exits, and Go may retire threads, so the goroutine that starts QEMU **locks its OS thread and also waits for the process**; the thread ends together with that goroutine, after the child is gone. `Kill` signals the group (`kill(-pid)`), falling back to `Process.Kill`.
  3. **Windows:** own console process group, no console window, and a **Job Object with `KILL_ON_JOB_CLOSE`** that only the controller holds a handle to, so the OS ends QEMU whenever the controller dies. (The process is assigned to the job right after it starts; QEMU starts no children in that window.)
  4. **macOS (and any Unix with `ForceReaper`, which is how it is tested on Linux):** QEMU runs under the hidden `controlsnack __reaper --parent <pid> -- <qemu> <args>`. The reaper starts QEMU in its own process group, reports QEMU's pid on file descriptor 3 (`CSREAPER/1 pid=N`) so the controller can kill **QEMU itself** rather than the wrapper, polls `getppid` every 200 ms (kqueue is not needed) and kills QEMU's group when the controller is gone or it gets SIGTERM/SIGINT/SIGHUP; it exits with QEMU's status. The reaper is not given `Pdeathsig` on Linux, because a wrapper killed without a chance to clean up would orphan QEMU.
  5. `Stop(ctx, quit, grace)` calls the QMP-quit callback, waits up to the grace period (3 s by caller), then kills; it returns only when the process is gone. `Kill` is idempotent and a no-op after exit.
- Verified: unit tests on Windows (real Job Object: controller killed ⇒ child gone) and on Linux with `-race` (Pdeathsig and the reaper path both: controller killed ⇒ child gone; kill under the reaper ends QEMU itself). Measured kill switch → supervised process gone: 0.5 ms (Windows), 0.3 ms (Linux). **Not run on macOS** (no machine); the reaper logic is OS-neutral Unix code and only `Setpgid` differs.

## D-47 — QMP client
- Status: Accepted (2026-10-12) · Type: Interpretation
- Context: PLAN P3-T05 lists greeting, `qmp_capabilities`, commands, events, `screendump`, `input-send-event` and `quit`, tested against a fake server. QMP can also run arbitrary monitor commands, add backends and devices, and start migrations.
- Decision:
  1. **The client sends only a closed allowlist of commands**: `qmp_capabilities`, `query-status`, `query-version`, `query-chardev`, `quit`, `system_powerdown`, `stop`, `cont`, `screendump`, `input-send-event`. Anything else is `ErrCommandNotAllowed` and nothing is written. Adding a command means adding it here with a test, the same rule as the QEMU argv allowlist.
  2. **Events are remembered** (last 256) so that waiting for one cannot lose a race with it: `WaitEvent` looks at the past first, and `WaitPortOpen(id)` follows the latest `VSERPORT_CHANGE` per port (it keeps waiting after a close, because the guest stub reopens the port when the agent is re-pushed). Waiters are released with the connection's error when it ends.
  3. Messages are newline-delimited JSON, at most 4 MiB each; a longer or non-JSON message ends the connection. Replies are matched by a numeric `id`; a reply nobody waits for is dropped; a caller whose context ends stops waiting but the connection stays up.
  4. `Quit` counts the connection closing as success (QEMU may exit before it answers). It is the graceful callback of `qemu.Process.Stop`.
  5. `Dial` retries until its context ends (QEMU creates the chardevs one by one and `wait=on` serves them in turn; a socket that exists but is not served yet is retried too). TCP endpoints must be `127.0.0.1`.
  6. `screendump` takes an absolute plain path and `png` or `ppm`; `input-send-event` takes at most 256 events built by `MoveTo` (absolute pointer scaled to 0..0x7fff over the screen, clamped), `Button` (left/middle/right/wheel/...) and `Key` (QEMU qcode names).

## D-48 — Launch with the selected accelerator and one TCG retry
- Status: Accepted (2026-10-12) · Type: Interpretation
- Context: PLAN §7.9 specifies selection, the launch window, the single retry and how the fallback is surfaced; it leaves open how per-attempt files are created, what counts as "fatal", and how a half-started VM is cleaned up.
- Decision:
  1. `vm.Launch(ctx, LaunchOptions)` takes everything environmental as a parameter: `Resolve` (accelerator choice), `Prepare(ctx, attempt)` (fresh socket dir or ports, fresh overlay, UEFI variable copy — the session supplies it), `Backend` (start QEMU, dial QMP, dial a chardev; `RealBackend()` is production) and `Events` (`AccelSelected`, `AccelFallback`). `AuditEvents` writes them as lifecycle audit records (`accel_selected {requested, chosen, tried[]}`, `accel_fallback {requested, from, used, reason, stderr}`) and forwards to a second listener (terminal warning, viewer notice).
  2. The launch window is 30 s, ×4 for tcg; inside it QEMU must be dialed on every chardev (all dials concurrent; when one fails the others are canceled and joined before cleanup), answer QMP, report `running` and stay running for 10 s (not scaled). Failure: process exit, QMP not ready, window expiry (the message says whether the VM ever reached running), or a state of internal-error, shutdown, guest-panicked, io-error, watchdog.
  3. **One retry, hardware accelerators only.** A failed attempt is killed, its output captured, the process waited for (5 s); its files are cleaned up before the next `Prepare`. **No retry** when the failure was tcg, when the caller's context ended, when the failed QEMU would not die (a second QEMU never starts beside a live one), or when the failure was ours (files could not be prepared, the command line was refused by the safety check; exit code 1) or QEMU could not be executed at all.
  4. Both failing ⇒ exit code 3 with both attempts' reasons and stderr excerpts (≤ 1 KiB each, the *end* of the output, with QEMU's `info: QEMU waiting for connection` chatter removed) and the hint to run `controlsnack doctor`.
  5. `VM.Stop` = QMP `quit`, 3 s, kill; `VM.Kill` = immediate; both release the connections and run the cleanup once. `AllocateEndpoints`: unix sockets inside a short private directory (`NewSocketDir`) on Linux/macOS, free loopback ports on Windows.

Fake-backend tests cover every branch; `-race` clean.

## D-49 — `controlsnack doctor`
- Status: Accepted (2026-10-12) · Type: Interpretation
- Context: PLAN §7.10 lists what the doctor reports and the cases it distinguishes; D-44 showed that the Windows optional-feature state does not predict whether WHPX works.
- Decision:
  1. **Structure.** Per-OS collectors (`doctor_{linux,windows,darwin,other}.go`) only gather `Facts`; the parsers of what the OS prints (`/proc/cpuinfo`, `/etc/os-release`, the WMI JSON, codesign output) are plain functions tested on every OS; `Diagnose(Facts, QEMUState, AccelResult)` is a pure function that returns notes, remediation steps and the verdict and is table-tested for every case of §7.10 on every OS; `DoctorService` ties them to the same `qemu.Discover` and `ResolveAccel` that `run` uses, so the verdict cannot differ from what a run does (tested for every setting). The probe constructor is injectable for tests.
  2. **Read-only and bounded.** Nothing is changed or installed; Windows facts come from the registry, `IsProcessorFeaturePresent`, `WHvGetCapability` and one non-interactive PowerShell WMI query run via `-EncodedCommand` (30 s); a denied or failing query is reported as a problem and the rest of the report stands.
  3. **The decision follows the probe, not the switches** (D-44): when the hardware accelerator worked, nothing is "fixed" even if an optional feature reads disabled; when it did not, the Windows cases are 1 firmware off and no hypervisor (BIOS, then the feature), 2 feature off (enable it; with a hypervisor running, "do not disable WSL2 or Hyper-V"), 3 feature on but no hypervisor reported (restart; `bcdedit /set hypervisorlaunchtype auto`), 4 everything on but QEMU's launch fails or the build lacks WHPX (install a current QEMU). "Off in the BIOS" is never said while a hypervisor is running.
  4. **Linux looks at `/dev/kvm` first** (found while testing in WSL2, where `/proc/cpuinfo` has no `vmx` yet `/dev/kvm` exists): existing-but-unopenable ⇒ `usermod -aG kvm $USER` (or re-login); CPU flags, module loading and nested-virtualization advice apply only when the device does not exist.
  5. **Exit codes.** 0 when a VM can run (any accelerator, tcg included); 3 when QEMU is missing, too old, lacks a device, or cannot start an empty machine with tcg; 2 when `--accel`/`--slow` are contradictory or name an accelerator the OS does not have (the doctor loads configuration without validating it, so it can diagnose broken setups).
  6. **Extra checks are pluggable** (`Check`, 10 s each): the base image (P3-T06), the viewer's browsers (P6) and local model servers (P5) register theirs when they land; until then the report has none. `--json` prints the whole `Report`.
  7. Long PATHs: `qemu.NotFoundError` counts the directories that simply lack QEMU instead of listing them (the full list stays in `Attempts`).
  8. CI: the macOS and Windows jobs install QEMU (`brew`, `choco`) and run `doctor --json` (must exit 0), keeping the JSON as an artifact — the first real evidence for HVF and WHPX on hardware.
- Verified for real: Windows 10 (edition, build, hypervisor running, firmware virtualization correctly false while a hypervisor runs, the three feature states, `WHvGetCapability` true; QEMU not found ⇒ verdict `cannot run a VM`, exit 3, install step); WSL2 against QEMU 8.2.2 (kvm refused for group membership, tcg chosen, exit 0).

## D-50 — Image manager and the Debian upstream
- Status: Accepted (2026-10-12) · Type: Interpretation (one deviation from PLAN §7.5)
- Context: PLAN §7.5 describes the pipeline and the image cache; Appendix B says to re-check Debian's release, URLs and whether a checksum signature exists before relying on them.
- Decision:
  1. **Verified today (2026-10-12):** Debian 13 "trixie" is stable; `https://cloud.debian.org/images/cloud/trixie/latest/debian-13-genericcloud-{amd64,arm64}.qcow2` exist (341,508,096 bytes for amd64, built 2026-10-01), `SHA512SUMS` lists both, `latest/` redirects (302) to an HTTPS mirror that honors range requests (`206`). **Debian publishes no signature for `SHA512SUMS`** (`.sign`, `.asc` and `.sig` all 404), so there is nothing to verify against a pinned key: the manifest records `signature_verified: false` with the reason, and the image is trusted on HTTPS plus the checksum list fetched from `cloud.debian.org` itself (the origin, not the mirror the image comes from). No PGP dependency is added.
  2. **Layout:** flat files in `<user cache>/controlsnack/images/`: `base-<id>.qcow2` and `base-<id>.json`; the id is the first 12 hex digits of the sealed file's SHA-256. The manifest has the PLAN fields (id, created, controlsnack_version, recipe_sha256, upstream {url, sha512, signature_verified (+ note)}, arch, sha256, size, packages) and is validated strictly on read and on import (nothing in an imported manifest is trusted: ids, URLs, package names are all pattern-checked; unknown fields and trailing data are errors).
  3. **Deviation:** a sealed image is `chmod 0400` (read-only, this user only) instead of the plan's 0444: the image is never written and QEMU runs as this user, so world-readable bought nothing.
  4. **Download:** HTTPS only, redirects only to HTTPS and at most five; resumable through `<file>.part` and `Range` (what is on disk is hashed first, so the SHA-512 comes out right without re-reading); a server that ignores `Range` means starting over, a wrong `Content-Range` is an error, `416` on a complete part finishes the job; an idle timeout (30 s without a byte) and a size cap (4 GiB, checked against the announced size and the bytes actually received); the destination only appears after the checksum matched. A resumed file that fails its checksum is retried once from scratch (the server's file may have changed); a fresh download that fails is final and nothing is kept.
  5. **Store operations:** `List` (newest first; unusable entries are reported, never fatal), `Find` by id prefix (≥ 4 digits, ambiguity is an error), `Newest(arch)`, `Resolve(vm.image, arch)` (empty = newest, an id, or a path to a qcow2 file used as it is), `QuickCheck` (existence and size — what `run` does every start; hashing 2+ GB each time would be absurd), `Verify` (full SHA-256, cancellable), `Remove`, `Import` (manifest valid, qcow2 magic, size and SHA-256 match, copied atomically, id not already present), `Commit` (used by the build to seal).
  6. `image rm|verify|path` with no matching image exit with code 4 (`ImageMissing`); `image import` of a file that does not match its manifest exits 1; `image path` prints the path and nothing else.

## D-51 — The seed ISO and the guest recipe
- Status: Accepted (2026-10-12) · Type: Interpretation
- Context: PLAN §7.5 step 4 lists what the seed contains; Appendix B asks to check the ISO library (go-diskfs) before relying on it. The recipe is what the first real image build (P3-T08) will exercise.
- Decision:
  1. **ISO library.** `github.com/diskfs/go-diskfs` v1.9.4, only its `filesystem/iso9660` and `backend/file` packages: **MIT** (the plan assumed Apache-2.0; both are on the allow-list) and a footprint of one more permissive module (`djherbis/times`) plus `x/sys`. Hand-rolling ISO 9660 + Rock Ridge + Joliet was rejected: the point of the seed is that Linux and cloud-init read it. Both extensions are enabled — without them the files would be named `USER_DAT`, which cloud-init does not read.
  2. **Findings while testing it.** go-diskfs's `Open`/`ReadDir` follow `io/fs` rules (unrooted names: `"."`, `"user-data"`; a leading `/` is "invalid argument"). The tests read the ISO with an independent reader written from the specification (primary and Joliet descriptors, UCS-2 names) and, where it exists, with `blkid` (`LABEL="cidata" TYPE="iso9660"`).

## D-52 — Building the image for real (P3-T08)
- Status: Accepted (2026-10-12) · Type: Deviation from D-50 / PLAN §7.5 (the upstream image) plus Interpretation
- Context: the first real build (WSL2 on the Windows dev machine, QEMU 8.2.2, software emulation) failed four times, each time for a reason no fake could have shown. The last one decided the choice of base image.
- Decision:
  1. **The base image is Debian's "generic" cloud image, not "genericcloud".** The genericcloud kernel (`linux-image-cloud-amd64`) is built without graphics and input support: in 6.12.107+deb13-cloud-amd64 `CONFIG_DRM` is not set at all, there is no `usb-xhci`/`usbhid`, and no emulated NIC drivers. The finished desktop image booted to a login prompt and never started X, so the boot check timed out after 8 minutes (the console showed LightDM "started" and nothing after it). `debian-13-generic-{amd64,arm64}.qcow2` carries the standard kernel (435 MB instead of 341 MB for amd64); verified 2026-10-12 that `SHA512SUMS` lists both and that the mirror honors range requests. The reason is written next to `DebianStable` so nobody switches back to save 90 MB.
  2. **The seven steps** (§7.5): preflight (QEMU, accelerator as `run` resolves it, ≥ 8 GB free, confirmation unless `--yes`), upstream lookup (skipped with "up to date" when an image of the same recipe and the same upstream checksum exists, unless `--force`), download, overlay + seed, provisioning boot, flatten (`qemu-img convert -c`), **boot check**, commit. One build at a time per user (`platform.AcquireLock`, pid + start time, stale locks are taken over). Everything the build touches is a field of `Builder` with a real default, so the stage failures (overlay, provisioning, convert, boot check) are tested with fakes and each leaves nothing behind.
  3. **The provisioning VM has what the runtime VM must not:** a display device (a q35 guest without one hangs after GRUB under tcg) and a NIC (`user,model=virtio-net-pci`, the guest's only way to `apt`). The NIC is a single exemption in `safety.AssertQEMUArgv` (`ProvisioningNIC`, provisioning profile only, exact string); the runtime profile still has `-nic none` and the checker still rejects every other NIC in both profiles.
  4. **Failures that real runs showed and tests now pin:** dpkg configuration-file prompts block a non-interactive install (`Dpkg::Options force-confdef/confold` in `apt.conf`; `TestTheBuildNeverStopsToAsk`); the provisioning script wrote every progress line twice (cloud-init also sends stderr to the console), so `say` writes the console only; `glib-compile-schemas` is in `libglib2.0-bin`, which `--no-install-recommends` leaves out; `signal.Notify` re-enables SIGINT and SIGHUP that the parent had ignored (a background job, `nohup`), so `handledSignals` leaves ignored ones ignored; QEMU does not quit when its stdin ends (the sandbox probe now sends `quit`); the VSERPORT_CHANGE event only names a port that has a device `id=` (`agent0`, `net0`).

## D-53 — Overlays, kept VMs and locks (P3-T09)
- Status: Accepted (2026-10-12) · Type: Interpretation
- Context: PLAN §7.6 gives one paragraph; the details below decide what can go wrong with a disk that two sessions or a moved base image could damage.
- Decision:
  1. **Overlays always name their base by absolute path** (`qemu-img create -f qcow2 -F qcow2 -b <abs> <overlay>`), because a relative backing file is resolved against the overlay's directory and breaks as soon as the base moves; a session overlay is deleted with its session.
  2. **Kept VMs** live in `<state>/vms/<name>/` with `disk.qcow2`, `vm.json` (name, base image id and path, arch, created, last used, version) and, on aarch64, `vars.fd`. Names are 1 to 40 characters of `a-z0-9-` starting with a letter or digit (they become directory names; the Windows reserved names are refused too). Generating a name for a bare `--keep-vm` belongs to the session (P7-T06).
  3. **Opening a kept VM checks two things:** its recorded base id equals the image `run` resolved (else `BaseMismatchError`, naming both), and the qcow2 header's backing file really is that image (`CheckBacking` reads the header itself, with the same-file test of the platform, so a swapped or deleted base is caught before QEMU fails with an unreadable message). A base given by path (outside the store, no id) cannot be the base of a kept VM.
  4. **One session per kept VM:** `Acquire` takes `<vms>/.<name>.lock` with `platform.AcquireLock` (pid + process start time, so a lock of a dead process, or of a pid that was reused, is taken over; a live one is "in use by process N"). `vm ls` shows name, base image, created, last used, disk size and a status (ok, base image gone, disk does not match its base); `vm rm` refuses a VM that a session is using, and removes the directory without ever following a link out of it.
  5. `platform.FreeSpace` (statfs / `GetDiskFreeSpaceEx`) and `platform.AcquireLock` are shared by the image build and the kept VMs.
- Verified: real `qemu-img` overlays (header parsing against what qemu-img writes), mutation checks on the base-id and backing-file tests.

## D-54 — The agent connection: dispatcher, installer and client (P3-T10)
- Status: Accepted (2026-10-12) · Type: Interpretation
- Context: PLAN §5.1 specifies the bootstrap, the frames, the handshake and the heartbeat; §7.7 says "reconnect when the bootstrap reopens the port". Writing the minimal agent and the client raised the points below.
- Decision:
  1. **`ping` is answered by `pong`**, the one request whose response is not `<name>.res` (`protocol.ResponseOf`, §5.1); the registry test pins it and that `ping.res` does not exist.
  2. **The dispatcher answers `ping` inline** on the reading goroutine, and **concurrency limits never stop the reader**: requests beyond `MaxInFlight` (default 8) wait for a slot inside their own goroutine (a cancel releases them), up to 64 running or waiting, after which the answer is `busy`. The first version blocked the reader at the limit; its test hung, which is how it was found: with the reader stuck neither pings nor cancels get through, so a busy agent would have been declared dead exactly when it needed to be cancelled.
  3. **Handler failures stay small:** a handler's own `*HandlerError` carries its protocol code; any other error is `internal` with its text cut to 1000 bytes of valid UTF-8; a panic becomes `internal` without its message (the log has it) and the agent lives on; a request the host cancelled is answered `canceled`; a second request with an id that is still running is `busy`; `id 0` requests are ignored (that id is for agent events); a second `hello` is refused.
  4. **A refused hello ends the session** (`ErrHandshake`; the stub then waits for a new push). An agent started without `--nonce` echoes the one it is given (tests only; the stub always passes it).
  5. **The host connects afresh every time** (`agentclient.Dialer`): the first connection is the one `Launch` already holds, every reconnect dials the chardev again. Closing the host's end is what makes a hung agent in the guest see end-of-file and exit (virtio-console reads return 0 while no host is connected), after which the stub's loop (which already sleeps and retries while the port reads as end-of-file) waits for the next push. Re-pushing on the old stream could not do that, and would have had to guess where the dead agent's last frame ended.
  6. **Every blocking step has a bound:** the push and the stub's verdict (`InstallTimeout`, 60 s), the handshake (`HelloTimeout`, 10 s), each single write to the port (`WriteTimeout`, 20 s: an agent that stops reading cannot block the host, and a failed write tears the connection down because a half-written frame cannot be repaired). `vm.Boot` multiplies them by the accelerator's timeout factor (4 under tcg).
  7. **Heartbeat:** a `ping` every 2 s with 2 s to answer; three misses in a row end the connection (`ErrAgentDown`); a late pong counts as a miss. The connection's context is derived with `context.WithoutCancel` from the `Connect` call, so a short connect deadline does not kill a connection that was made in time.
  8. **Everything the agent sends is checked:** the response type must be `<request>.res` (or `error`), bodies decode strictly (unknown fields are errors), error codes and messages are clipped to 300 runes before they reach a message, answers to unknown ids and malformed events are ignored, and a wrong type, a malformed body or an oversize frame drops the connection (`ErrBadResponse`). A request the host refuses to build (a blob over 8 MiB) is a local error and costs nothing.
  9. **`Supervise`** re-establishes the connection with a pause that doubles from 500 ms to 5 s; `OnState` reports connecting, up and down(err); calls made while down fail at once with `ErrAgentDown` (whether to wait is the session's decision).
  10. **One test hook in the guest stub, `CS_PORT=-`** (file descriptor 3 is already the port), makes the real `bootstrap.sh` testable against the real compiled agent and the real client over a socket pair (Linux only): install, the file's place and mode, the hash check, the handshake, ping, the stub's refusals (`arch-mismatch-<arch>`, `sha256-mismatch`, `bad-line`) and the stub taking the agent's end as its cue to wait for the next push.
- Verified for real: in a booted guest on the real image, the 2.9 MB agent is pushed over virtio-serial, hash-checked by the real stub and shakes hands within about 2 s under tcg (D-55).

## D-55 — Booting a session VM, and `run --no-llm --viewer none` (P3-T11)
- Status: Accepted (2026-10-12) · Type: Interpretation
- Context: PLAN §12 asks for a milestone before the viewer and the model exist: the VM side of a session, end to end. `internal/session`'s placeholder runner now does it; every other `run` combination still exits 70.
- Decision:
  1. **`vm.Boot`** = `Launch` + wait for the guest to open `agent0` (the QMP event; QEMU dying first ends the wait at once, with its output and the console tail) + install and handshake + `Supervise`. It returns a `Machine` with the timings of each stage, which become the terminal summary, the audit `ready` record and the metrics. `NewPrepare` (sockets or loopback ports, overlay, aarch64 variable store per attempt) is shared with the image boot check. Waits are multiplied by 4 under tcg, like the launch window.
  2. **The runner's order matters:** configuration checks (QEMU, image, embedded agent, resolution) → the kill switch exists → a loopback-only control endpoint (`/control/kill`, the handler the viewer will mount later, token from the lock) → the session lock (one session per user, D-20; a stale one is reaped) → the audit log (`start`) → the session directory → boot. `controlsnack kill` from another terminal therefore asks the session to die, instead of killing the controller from outside.
  3. **How it ends decides the exit code:** Ctrl+C, SIGTERM or `controlsnack kill` → kill switch → **5**; session timeout → **6**; the guest powering off → 0; QEMU dying by itself → 1; no QEMU or accelerator → 3; no image → **4** with the command to build one; a missing embedded agent → 1 with `go run ./tools/dev agent`. The audit log always ends with an `end` record (an error is recorded in it), so `audit verify` calls every session complete; a log without one means a crash.
  4. **Found by a test, then confirmed as a real risk:** a kill from outside makes QEMU exit before the context is cancelled, and the first version of the wait loop reported that as "QEMU stopped by itself". The loop now asks the kill switch first (it sets its flag before it kills QEMU), and agent-connection messages stop once it has fired.
  5. **Session files** live in `<state>/run/<id>/` (overlay, serial log, screendump `ready.png`, UEFI variables on aarch64), not in `/tmp`: an overlay grows to gigabytes. A `.running` marker says a session owns the directory; the next start sweeps directories that still have it (the controller was killed hard), and `--keep` removes only the marker.
  6. **VM names** may not contain `_`, session ids do (`s_1a2b3c4d`): the QEMU name is the id with hyphens. `NewPrepare` validates it up front. (The first real run failed on this.)
  7. **The screendump** is taken through QMP right after the handshake and its PNG header is read to report size and dimensions; failing is a warning, not an error, because it proves a capability, not the session.
- Measured for real (WSL2 Ubuntu 24.04 on the Windows dev machine, QEMU 8.2.2, **tcg**: this user cannot open `/dev/kvm`, so "detected" and `--slow` are the same accelerator here): QEMU running after 10 s (the stability window), desktop up after 58 to 68 s, agent connected after 61 to 70 s (three runs: CLI, CLI with `--slow`, e2e), kill to QEMU gone 14 to 17 ms (SIGTERM, `controlsnack kill`, `Machine.Kill`), exit code 5, no lock, directory or process left. `doctor` and `run` chose the same accelerator. The desktop screendump (1280x800) shows the XFCE panel, the launcher dock and the desktop icons on a black background (no wallpaper package is installed).
- Not measured: an accelerated boot (KVM, WHPX or HVF): nothing here can use one; CI doctor artifacts and the first hardware run will tell.

## D-56 — The agent's worker pools (P4-T01)
- Status: Accepted (2026-10-13) · Type: Interpretation
- Context: PLAN §8 gives the worker counts per category (capture 1, input 1 serialized, a11y 1, OCR 1, exec 2, browser 1, wait_for 1) and says `ping` is always immediate and `cancel` aborts by id. P3-T10's dispatcher had one global limit.
- Decision:
  1. **A pool is a first-in-first-out queue with N workers.** A semaphore would not do: goroutines waiting on it are not served in arrival order, and `input` is only correct if two requests run in the order they were sent. Workers are started when there is work and leave when the queue is empty (an idle agent holds no goroutines); the count drops under the same lock that finds the queue empty, so a request pushed a moment later starts a new worker instead of waiting for one that left. A mutation test (serve the newest first) fails `TestInputIsSerializedInOrder`.
  2. **Categories** (`server.PoolOf`): `capture` = screenshot, screen_info, windows; `input`; `a11y` = a11y_tree, a11y_action; `ocr`; `exec`; `browser`; `wait_for`; and, beyond the plan's list, `file` (file_peek, 2 workers: it is a small read the exec policy needs while a command runs) and a spare pool for types without a category. `Config.Workers` overrides the counts (tests, tuning).
  3. **Cancel is exact:** a request still waiting is taken out of its queue, answered `canceled` at once and never reaches its handler; a running one gets its context cancelled and answers itself. The total of running and waiting requests is capped at 64 (then `busy`), as in D-54.
  4. **The session ending drops the queue:** workers skip jobs once the connection's context is done, so nothing queued runs for a host that has gone, and `Serve` still waits for the workers that are mid-handler.
  5. **Capabilities are derived from the registered handlers** (`server.CapabilityOf`), plus ping and the explicit extras (netproxy is a feature, not a request type), sorted and without duplicates. The agent cannot announce a capability it has no handler for, and cannot forget one it has.
  6. **Logs** go to stderr as JSON (the journal, in the guest); `--log-level` or `CS_LOG_LEVEL` sets debug/info/warn/error. Each request logs type, id, pool, queue time, run time and outcome, at debug when it succeeded and at warn when it did not. **Bodies, results and error text from commands are never logged**: they hold what the model typed and what the screen showed (tested with a command and an output that must not appear).
- Verified: pool isolation (a slow exec does not delay a screenshot; the third exec waits for one of two workers), input order and peak concurrency 1, cancel of a queued request, a session that ends with a queue, capabilities, the log content; green under `-race` (5 runs).
- Supersedes / superseded by: amends D-54 item 2 (the global in-flight limit became per-pool queues; the cap of 64 stays).

## D-57 — Screen capture and the WebP encoder (P4-T02; settles D-11)
- Status: Accepted (2026-10-13) · Type: Interpretation (completes D-11)
- Context: D-11 left the encoder to a benchmark "on real guest screenshots"; PLAN §8 asks to verify that `kbinani/screenshot`'s Linux backend is cgo-free, otherwise to use xgb directly.
- Decision:
  1. **Capture goes through `jezek/xgb` directly** (BSD-3, the maintained fork of BurntSushi/xgb): `GetImage` of the root window, `QueryPointer` for the cursor. Verified 2026-10-13: `kbinani/screenshot`'s Linux backend is cgo-free (only its macOS file imports "C"; it uses jezek/xgb and gen2brain/shm), but it brings Wayland and D-Bus code and a second X connection, and the agent needs xgb itself for EWMH, XTEST and RandR. One connection, one dependency.
  2. **One pixel format is accepted:** 32 bits per pixel, 24-bit true colour with masks 0xff0000/0xff00/0xff, least significant byte first (what Xorg gives). Anything else is `ErrUnsupportedFormat` at start-up, not a silently wrong picture. The unused fourth byte is set opaque (an encoder would take X's leftover for transparency). The capture buffer is reused; no MIT-SHM yet (a 1280x800 capture with the PNG encode took 312 ms under tcg in the real guest; SHM is for the performance pass, P8-T04, if the numbers ask for it). X does not draw the pointer into a capture, so the cursor is a separate field.
  3. **The corpus is real:** eight screenshots of the guest (bare desktop, terminal with text, file manager, text editor) at 1280x800 and 1920x1080, driven through QMP key events (`TestE2ECollectScreens`, `-tags e2e`). Benchmarked on this machine (i7-10870H, Go 1.26.9, five runs, median); PSNR is measured with one neutral decoder (`x/image/webp`, with the limited-range BT.601 conversion VP8 needs; the first run of the benchmark read 23 dB for every lossy WebP because Go's `image.YCbCr` assumes full range, and `gen2brain`'s own decoder returns planes, even for lossless files).
  4. **Results, 1920x1080, "terminal and file manager windows" / "terminal only" scenes:**

     | encoder | bytes | ms | PSNR |
     |---|---|---|---|
     | `deepteams/webp` q70, method 4 | 55,894 / 47,598 | 50 | 39.6 / 41.0 dB |
     | `gen2brain/webp` q70, method 4 | 56,836 / 47,960 | 600 | 41.6 / 44.0 dB |
     | JPEG q70 (stdlib) | 129,193 / 109,397 | 35 | 38.2 / 39.6 dB |
     | PNG (fastest) | 137,823 / 104,687 | 45 | lossless |
     | WebP lossless (`gen2brain`) | 52,288 / 28,214 | 1,200 / 220 | lossless |

     A bare desktop is 8 KB. The budget "< 200 KB per 1080p WebP q70 screenshot" holds with a factor of three.
  5. **Decision: `deepteams/webp` v1.2.8 (MIT), lossy, quality 70, method 4.** It is ten times faster for the same size (what matters in a guest that may run under tcg, where everything is 10 to 50 times slower, and at 5 frames per second); it adds 1.2 MB to the agent instead of 3.7 MB and no dependency; its files are accepted by the reference libwebp (decoded with `gen2brain`'s libwebp-based decoder on all eight images: 38 to 43 dB). `gen2brain/webp` is 2 to 4 dB better at the same size, but its "uses the system libwebp via purego" advantage did not engage in a `CGO_ENABLED=0` Linux build (the same 600 ms with and without the `nodynamic` tag, with libwebp.so.7 installed), so what remains is the transpiled Go at 600 ms. Method 4 is where effort stops paying (0 to 2 are slower and larger, 5 and 6 give the same bytes, 3 is 12 % faster for 3 % more bytes); the default preset beat `text` and `drawing`. Revisit if the model's reading of text turns out to need the extra 2 dB: lossless WebP is an option because screens compress very well (28 to 52 KB) but costs 0.2 to 1.2 s.
  6. **The `screenshot` request** validates everything before it touches the screen (format, quality 0 to 100 with 0 meaning 70, `max_long_edge` 0 or 32 to 7680, `if_changed_since` as 16 lower-case hex digits, unknown fields); hashes the raw capture (maphash over the size and every row, random seed per process, so hashes are only comparable within one agent) and answers `unchanged` with no picture when the host's hash matches, before any scaling or encoding; scales with `x/image/draw` BiLinear (never up, aspect kept, the response carries the factor); refuses an encoding over the 8 MiB blob limit with advice instead of sending a frame the host would reject; `marks_generation` is `unsupported` until the accessibility service exists (P4-T06/T07).
  7. **The agent announces `screenshot` only when it could open the display** (`DISPLAY` and `XAUTHORITY` are inherited from the session); otherwise it logs why, still answers pings, and reports the screen size it found in the handshake (`--screen-size` overrides it, for tests).
- Verified for real: in the guest, the agent's PNG matches QEMU's own screendump (within 1 % of the pixels, for a clock that ticks), `if_changed_since` gives `unchanged` plus the cursor, JPEG and WebP of 640 px and of the whole screen come back; WSL's X server (WSLg's XWayland) accepts `Open` and `QueryPointer` but answers `BadMatch` to reading the root window, as Wayland compositors do, so the capture integration test skips there and runs under Xvfb in CI.

## D-58 — Windows and monitors: EWMH and RandR (P4-T03)
- Status: Accepted (2026-10-13) · Type: Interpretation
- Context: PLAN §8 says to read EWMH directly with xgb (no xgbutil), to focus and maximize with ClientMessages and to read monitors from RandR. The first run against the real window manager (xfwm4) showed what the plan could not.
- Decision:
  1. **The list is `_NET_CLIENT_LIST_STACKING` reversed**, so the window in front comes first (EWMH is bottom to top); `_NET_CLIENT_LIST` is the fallback; with no window manager the list is empty, not an error. At most 100 windows are read, each with its nine requests (name, old name, class, pid, frame extents, state, type, geometry, position) in flight together.
  2. **Shell windows are left out.** xfwm4's client list also holds the three windows of xfce4-panel and the desktop background (`Xfdesktop`, the size of the screen), and they sit on top of the stacking order. A window whose `_NET_WM_WINDOW_TYPE` is only DESKTOP, DOCK, TOOLTIP, DROPDOWN_MENU, POPUP_MENU, COMBO, DND or NOTIFICATION is `Shell`: not listed, not the active window, and `focus` or `maximize` on it answer `not_found`. A window with no type, or with any other type among its preferences, is a normal one.
  3. **What a window says about itself is cleaned:** the title is `_NET_WM_NAME` (else `WM_NAME`), the class is the class half of `WM_CLASS`; control characters and invalid UTF-8 are dropped, white space runs become one space, 256 and 128 characters at most. It stays untrusted text: a title can say "ignore previous instructions", and the host fences it (§6.10). Bounds are the client rectangle plus `_NET_FRAME_EXTENTS`, in screen pixels, so they match what a screenshot shows.
  4. **Ids** are `0x` and lower-case hex; nothing else parses, and an id must be in the current list, so the host cannot make the agent send a message to an arbitrary X window.
  5. **Focus** is a `_NET_ACTIVE_WINDOW` ClientMessage to the root window with source indication 2 ("a tool", which window managers honor); **maximize** adds `_NET_WM_STATE_MAXIMIZED_VERT` and `_HORZ`. Both then poll for 1.5 s until the window manager shows the effect and answer `timeout` when it does not, instead of reporting success for something that did not happen. A request that the host canceled stays a cancellation.
  6. **Monitors** come from RandR 1.5 `GetMonitors` (active ones); without it, or with none, the screen is one monitor. The guest's single virtual output has no primary flag set, so when none is flagged the first monitor is primary (found in the first real run).
  7. **`screen_info`** adds the pointer and the focused window; no focused window and no readable pointer are facts, not failures.

- Not covered: more than one monitor (the logic is unit-tested, no multi-monitor X server was available), moving, resizing and closing windows (not in the protocol).

## D-59 — Input: XTEST, keys and Unicode typing (P4-T04)
- Status: Accepted (2026-10-13) · Type: Interpretation
- Context: PLAN §8 specifies XTEST for pointer and keys, keysyms resolved through the keyboard mapping, Unicode by a borrowed keycode, gestures with timings and the screen hash after the input. Several things the plan leaves open came up while building and testing it.
- Decision:
  1. **A request is validated whole before anything is sent**, so a refused request does nothing at all: at most 64 events, 4000 characters of text in all, scroll at most 20 notches, key repeat 1 to 20, every coordinate inside the *current* screen (the size is read per request), buttons left, middle or right, a key combination that parses, and no control characters in text (only newline, carriage return and tab are keys). A drag is an event type of its own (`drag`: press at x, y, move to `drag_to`, release); `down`, `up`, `click` and `drag` move the pointer to their position first.
  2. **Pointer and buttons through XTEST** (absolute motion, buttons 1 to 7: wheel up and down are 4 and 5, left and right 6 and 7). Each fake event is sent checked, one round trip each, so an error surfaces at the event that caused it. Timings: a click holds 12 ms, a double click is two clicks 60 ms apart (the desktop's interval is 400 ms), 8 ms between wheel notches, a drag goes in ten steps of 20 ms with 30 ms before and after (about 260 ms in all), and keys are pressed and released 10 ms apart (xdotool uses 12). A button that was pressed is always released, also when a step fails or the host cancels.
  3. **Key combinations are xdotool's**: `ctrl+l`, `alt+F4`, `Return`, `ctrl+shift+t`, `ctrl++`. Modifiers are ctrl (control), alt, shift, super (win) and altgr, in any case; one other key at most; named keys in any case (`return`, `Page_Down`, `f12`, `kp_5`), a single character exactly as typed, so `L` is shift and `l` as in xdotool. Keysyms are resolved through the live keyboard mapping, read again for every request that types (that picks up layout changes without watching MappingNotify): the plainest route wins (lowest column, then lowest keycode), AltGr is supported, and the legacy EuroSign keysym stands in for the Unicode one.
  4. **Unicode typing borrows a keycode**, as `xdotool type` does: the highest keycode that has no keysym gets the character's keysym in every column (Unicode keysyms are 0x01000000 plus the code point), the server is synchronized, clients get 15 ms to refresh their keymap, the key is tapped, and the keycode is given back at the end of the request; a repeated character is not remapped again. The plan's "xdotool type as fallback" is not built: the borrowed keycode worked in the guest's GTK applications, and the fallback can be added behind `exec` (P4-T05) if an application ever shows otherwise.
  5. **No key is ever left down.** A modifier that stays down turns the user's next keystrokes into shortcuts, so every request ends by releasing whatever is still held (last pressed first), after success, failure or cancellation. Two bugs of the first version were found by tests: a key that was dropped from the held list *before* its release succeeded would never be released again (a failed release now stays on the list and is retried), and a character's own shift released a shift that the combination itself held (a tap now releases only what it pressed).
  6. **The event queue is drained.** xgb stops reading from the socket when its event queue is full, and every keymap change sends this client a MappingNotify; a goroutine drops the events.
  7. **`screen_hash_after`** is the hash of the screen after the last event, from the screenshot handler's hasher, so it can be compared with a later screenshot's hash (and in the real guest it is: the next screenshot with `if_changed_since` answers `unchanged`). It is taken 120 ms after the last event and, while the screen is still as it was before the input, again every 100 ms for up to 500 ms: the effect of a click shows a moment later, and "nothing changed" is information the host uses (loop detection, PLAN §6.6), not something to report because the screen was looked at too early. An unreadable screen gives an empty hash, not an error.
  8. **A failure says how far it got:** "event 3 (click) failed after 2 earlier ones ran". A key name the keyboard cannot type is the caller's mistake (`invalid_args`); anything else is `internal`.
- Verified for real (xfwm4, xfce4-terminal in the guest): a typed `héllo wörld 日本語 😀 € ñ` reads back exactly from the terminal's window title (set by an escape sequence in the typed command, read through `windows`); BackSpace with repeat 2; `ctrl+alt+t` opens a terminal and `ctrl+c` ends a command; a click on a title bar focuses the window; a drag moves a window by exactly (300, 150); the hash after the drag equals the next screenshot's.
- Not verified: scroll, middle and right clicks and double clicks against an application (the event sequences are unit-tested).
- Finding for the image: the guest has no CJK font, so characters that are typed correctly display as empty boxes in screenshots (`fonts-noto-cjk` is about 60 MB): decide at the image rewrite (P4-T13).

## D-60 — The exec runner and `file_peek` (P4-T05)
- Status: Accepted (2026-10-13) · Type: Interpretation
- Context: PLAN §8 says `bash -lc` with `Setpgid`, SIGTERM then SIGKILL after 2 s, output capped at 64 KiB per stream (head 48 KiB, tail 16 KiB) and a quiet environment. The plan does not say how output is collected; that choice decides whether the usual way a model starts a program works.
- Decision:
  1. **Output goes to private files, not pipes.** With pipes, a program the command starts in the background (`thunar &`, `chromium … &`, the idiom a model will use all the time) holds the pipe open: either the exec waits for it, or (with a wait delay) the pipe is closed and the program dies of SIGPIPE at its next write. With files the exec waits only for the shell, the background program keeps writing harmlessly, and the head and the tail of a long output can be read without holding it in memory. The files live in a 0700 scratch directory that is removed afterwards; stdin is a file too (or `/dev/null`).
  2. **A stream is capped at 64 KiB by default (1 to 128 KiB on request): the first three quarters and the last quarter**, with a line saying how many bytes were left out. Because a stream can grow while the command runs, the agent checks its size every 100 ms and stops the command when one stream passes 256 MiB (the notice is added to stderr): a runaway writer must not fill the disk while the caller waits for the timeout.
  3. **Output is cleaned**: terminal escape sequences (colors, cursor movement, window titles, links) are removed, every other control character except newline, tab and carriage return becomes U+FFFD, and invalid UTF-8 does too. A model gains nothing from escape codes, and the cleaning bounds the encoded size: a control character costs six characters of JSON (`\u0001`) and the response header is limited to 1 MiB, so 2 × 128 KiB of control bytes would otherwise make a reply the host cannot receive. The worst case is now three bytes per character.
  4. **Time limits:** 60 s by default, 100 ms to 10 minutes on request. At the end (or when the host cancels) the whole process group gets SIGTERM and SIGKILL 2 s later; once the shell is gone the rest of the group is killed too. A timeout is a result (`timed_out`, exit code 124 as `timeout(1)` does), a cancellation is the dispatcher's `canceled`. A normal exit does **not** touch what the command left in the background.
  5. **Exit codes follow the shell:** the status, or 128 plus the signal that killed the shell. **Environment:** the agent's own (so `DISPLAY` and the session bus reach GUI programs) plus `TERM=dumb PAGER=cat GIT_PAGER=cat DEBIAN_FRONTEND=noninteractive`, run as a login shell. **Directory:** `/home/cs/work` (the home directory if that is missing); a relative `cwd`, a missing one or a file is `invalid_args`.
  6. **The agent applies no policy.** Whether a command may run is the host's decision (§6.3); the agent refuses only what it cannot carry: a command over 16 KiB or with a NUL, stdin over 64 KiB, a timeout or output limit out of range.
  7. **`file_peek`** (the guest half of the script analysis of §6.3, wired in P7-T06): absolute paths only, symbolic links followed (the policy sees what the shell would run), regular files only, decided by `stat` before anything is opened so a pipe can never block the worker; the head (up to 64 KiB, default 64 KiB) is the response's attachment, the size is reported, a missing file is `exists: false`, a directory or device exists with size 0.
  8. **Unix only:** process groups come from `Setpgid`; elsewhere the runner answers `unsupported` (the agent runs in the Linux guest).
- Verified for real (the guest): the command runs as `cs` in `/home/cs/work` with `DISPLAY` set and the quiet environment; stdin and `cwd`; a timeout after 1.5 s with exit code 124; a canceled `sleep` leaves nothing running (`pgrep` finds none); `seq 1 100000` keeps head and tail; `thunar … & echo launched` returns at once and the file manager has a window 40 s later; `file_peek` of `/etc/os-release`, of a missing file and of a directory.
- Not covered: a command that detaches into a new session (`setsid`) survives a timeout (it is no longer in the group); resource exhaustion by a fork bomb is the exec policy's to deny, the VM's limits are the backstop.

## D-61 — Accessibility: AT-SPI over D-Bus, generations, actions (P4-T06)
- Status: Accepted (2026-10-13) · Type: Interpretation
- Context: PLAN §8 says to walk the AT-SPI tree of the active window, keep showing and visible nodes that are interactive or carry text, cap nodes, depth and time, number the nodes per generation, and act through `DoAction`, `GrabFocus` and `EditableText`, falling back to the pointer and the keyboard. The plan leaves open how the walk is bounded, what counts as worth reporting, and what an id means once the screen has moved on.
- Decision:
  1. **The walk goes level by level** (`a11y.Walk`), reading each level concurrently (eight bus calls in flight) and assembling the answer in document order (a parent, then its children, siblings in order). A first version walked depth first with free-running goroutines; when a limit cut in, *which* elements were left out depended on which call answered first, so the same window gave different trees. Level by level, what a limit leaves out is the deepest and last elements, always the same ones (tested 25 times with random latencies, and mutation-checked). Limits: 150 nodes by default (1 to 400), depth 30 (at most 60), at most four times as many elements looked at as nodes asked for, and a time budget of 1.5 s by default. The host may pass `budget_ms` (100 to 30000): the same tree takes several times as long without hardware acceleration (the guest under tcg needs about 25 ms per element), so the host scales the budget by the accelerator. Running out of time is not an error: what was found comes back with `truncated`.
  2. **What is worth reporting.** Nothing that is not showing and visible, and nothing below it (the contents of a closed menu are not on screen). Layout roles (filler, viewport, scroll pane, separator...) are skipped but their children are visited. Operable roles (push button, check box, menu, entry, text, slider...) are reported even without a name. Table cells, list items, tree items and icons are reported only with a name or description (a table of folders has four cells per row and one carries the name). Structural roles (panel, tool bar, table...) only with a *name*: toolkits put the tooltip of a button on the panel around it, which listed every toolbar button twice. An element with no area (no Component interface, or zero size) cannot be seen or clicked and is left out. Both rules came from reading real Thunar and Mousepad trees.
  3. **Text from applications is cleaned and bounded** (`internal/agent/textclean`, shared with the window titles): controls and invalid UTF-8 dropped, white space collapsed, names 300 characters, descriptions 200, values 500. **A password field's text is never asked for.** The answer is also cut to 700 KiB of JSON, since JSON writes `<` in six bytes and the protocol header limit is 1 MiB.
  4. **Ids and generations.** Ids are `a1`, `a2`... in document order; every tree request starts a new generation `g<n>`. The agent keeps the last four generations, so a batch of actions planned from one observation is not refused because a tree was read in between. An action first reads the element again: if it is gone, off screen, or has another role or name than it had when shown, the answer is `stale_element` (a new protocol error code); an unknown generation is `stale_element`, an id the generation does not have is `not_found`. Whether an older-but-kept generation is acceptable is the host's call (it knows the latest).
  5. **Scopes.** `active_window`: the application whose process owns the active window (`_NET_WM_PID` matched to the bus peer's process id), and in it the window it calls active, else the one with the window's title, else all its windows; with no match by process, only a window with the title. `desktop`: every application's windows on screen. `browser` is the browser tool's (`invalid_args` here). An empty tree says why in `note` ("no window has the keyboard focus", "the application of the active window does not expose accessibility information; use the screenshot, or OCR").
  6. **Actions.** `click`: for buttons, check boxes, radio buttons, menu items, links, tabs and switches, the element's own action (`click`, `press`, `activate`, `jump`, `toggle`... matched case-insensitively), otherwise a click in the middle of the element *as it is now*, through the input handler (same validation, same release of what was pressed). Lists, trees, tables and text are clicked, not actioned: their actions mean "open" and "edit", not "select". An element that is still busy with its action after two seconds (a button that opened a dialog and waits in it) did it: that is success, and no second click follows. `focus`: `GrabFocus`; if refused, a click only for elements that take text (a click on anything else could press it). `set_text`: only on an element that says it is editable; `EditableText.SetTextContents`, then the text is read back (never for a password field), and if the field did not keep it, select all (`ctrl+a`) and type. Text up to 4000 characters, line breaks and tabs allowed, other controls refused. The text is never put in an error message or a log line. The answer says how it was done (`action:click`, `pointer`, `editable_text`, `keyboard`).
  7. **The bus.** `Dial` asks the session bus for the accessibility bus (`org.a11y.Bus.GetAddress`; `AT_SPI_BUS_ADDRESS` overrides) and speaks AT-SPI with `godbus/dbus` v5.1.0 (BSD-2; v5.2.3 does not build for windows or darwin). An element's role, states and properties are asked as three calls in flight together. D-Bus errors map to "does not have this interface" (`ErrUnsupported`) and "no longer exists" (`ErrGone`). The connection is made when first used and again after it breaks (`LazyBus`: the agent starts with the session, and the accessibility bus may come up later). Outside Linux `Dial` is a stub answering `ErrUnsupported` (D-01).
  8. **Role names are a table of AT-SPI's own numbers** (`atspi-constants.h`, 0 to 130). The first version, written from memory, was off by one from role 21 (`FOCUS_TRAVERSABLE`); the tests now carry anchors written out so a shifted table cannot agree with itself, and the end-to-end test compares the table with `GetRoleName` for every role seen in the guest. The names are ATK's, which current ATK takes from its role enum: `button` (not `push button`), `statusbar`, `accel label`, `editbar`, `embedded`; the first two were found wrong by that test, the others follow from the ATK header.
- Verified for real (Mousepad and Thunar, GTK3, in the guest): the tree of the active window and of the desktop; the editor text read and set through EditableText (Unicode read back exactly) and cleared; a menu opened by its own action; a pointer click on a list row; every refusal; stale after the application closed; the 25 role numbers the bus produced all match `GetRoleName` (two names corrected: `button`, `statusbar`). A tree takes 0.6 to 2 s under tcg (about 25 to 35 ms per element plus 0.5 s).
- Not covered: Qt and Electron applications (none in the image), Chromium's own tree (the browser tool's, P4-T08), applications that expose no Component (their elements are dropped), the `Selection` and `Table` interfaces.

## D-63 — Text recognition with tesseract (P4-T07)
- Status: Accepted (2026-10-13) · Type: Interpretation
- Context: PLAN §8 says `tesseract <png> stdout -l eng --psm 11 tsv`, words grouped into lines, confidence under 40 dropped, ids `o<n>`, a cache by screen hash, a 10 s timeout, an optional region. It leaves open how the picture is prepared, how words become pointable things, and what is slow.
- Decision:
  1. **The program** (`ocr.Tesseract`) is run as `tesseract stdin stdout -l <lang> --psm 11 tsv` with the picture on its standard input: no temporary files. `OMP_THREAD_LIMIT=1`, because its threads fight over the few CPUs of the virtual machine. Output is capped (8 MiB; 4 KiB of its messages). The limit is a `Write` method on a type that does *not* embed `bytes.Buffer`: `io.Copy` finds the buffer's `ReadFrom` and fills it without asking (the flood test found this). The TSV parser is strict (the header, numeric columns, at most 20000 rows): output of a program that is not tesseract, or that stopped half way, is an error, not text from the screen.   5. **Time.** 10 s by default, as in the plan, and the request may carry `budget_ms` (1 to 120 s): the host scales it by the accelerator, since the whole screen takes about 14 s without hardware acceleration.

## D-64 — The browser tool: Chromium over a pipe, ids per tree, places from the page (P4-T08)

- Decision:

  5. **`ax_tree`**: Chromium's accessibility tree, reduced to what a person can operate (buttons, links, fields, options, tabs, switches, sliders, menu items...) and to named headings, images, dialogs and alerts; ids `w1`, `w2`... in document order; role names are the browser's own (`button`, `link`, `textbox`, `heading`...). An id is refused as `stale_element` when the active tab is not the tree's, when the element has left the page (the browser says the node or frame is gone), or when its role or name changed; an id the tree does not have is `not_found`. Navigating, going back and clicking a link all make the old ids stale.
  7. **Click**: by id, scroll into view and press the left button at the middle of the border box through the protocol (not through the display, so a covered window or a missing pointer does not matter); by selector, the first match (`not_found` if none, `invalid_args` for a selector the browser rejects). **Type** *replaces* what the field holds (select all, then insert, or delete when the text is empty), because a person who selects a field and types does that and a model that wants to add to a field says so by reading it first; `submit` then presses Enter; a line break goes into a text area. After a click or typing the service waits 400 ms for what it started (a navigation) before it reports where the page is.

## D-65 — Waiting inside the guest (P4-T09)
- Status: Accepted (2026-10-13) · Type: Interpretation
- Context: PLAN §8 says `wait_for` polls every 250 ms: `screen_change` (hash), `screen_idle` (no change for `value` ms, default 1000), `text_visible` (accessibility names first, recognition at most every 2 s), `window_title`, `element`; at most 60 s. The model-facing tool adds `seconds`.
- Decision:
  1. **Conditions.** `seconds`: the value is a number of seconds, 0.1 to 60, and the wait is always met. `screen_change`: met when the screen's fingerprint differs from the one at the first look. `screen_idle`: met when it has not changed for `value` milliseconds (100 to 60000, default 1000). `window_title`: met when any window's title contains the value, ignoring case. `element`: met when an element with the value in its role, name, description or value exists anywhere on the desktop's accessibility tree. `text_visible`: first the accessibility names of the window that has the focus (cheap), then, at most every 2 s and only if the screen has changed since the last reading, recognition of that window's region (the whole screen when the window is unknown or off the screen). `timeout_ms` is 100 to 60000, default 10000. A wait that ends unmet is an answer (`met: false` and the time waited), not an error; a cancellation stops it at once.
  2. **A probe starts no generation** (`a11y.Service.Probe`): polling a tree four times a second would otherwise use up the four generations the agent keeps and make stale the ids a model holds from a tree it read before the wait. For the same reason recognition goes through a `Contains` that shares the `ocr` handler's cache.
  3. **Every capture is a picture of its own.** The screenshot, input, text recognition and waiting workers all read the screen, in different pools, and `x11.Conn.Capture` handed all of them one shared buffer: one worker could be hashing or encoding while another overwrote it. It allocates a picture per call now (4 MB at 1280x800, a few a second at most).
  4. **Limits.** A screen that is never still (a blinking cursor, an animation, a clock with seconds) is never idle; this is the model's to know and the image's to avoid (see TODO). Recognition under tcg takes 8 to 14 s, so `text_visible` for text the accessibility tree does not have needs a long timeout there; the budget of one reading is the time left (1 to 120 s), and a reading too slow for it ends the wait unmet. The look interval is 250 ms plus the time to look (a capture takes about 50 ms natively, 300 ms under tcg).
- Verified for real (the guest): `seconds`; `screen_idle` met after 2.3 s on a quiet desktop; `screen_change` met 6.9 s after a window was scheduled to open in 4 s (the terminal needs its time to draw); `window_title` met at once for a window already there and unmet after exactly the timeout for one that never comes; `text_visible` found "waiting" in a terminal in 0.4 s through the accessibility names, with no recognition; `element` met 7.8 s after an editor was started and unmet for an element nobody has; refusals; a wait the host cancels stops and the worker serves the next one.
- Not covered in the guest: the recognition branch of `text_visible` (covered by unit tests with a clock that moves only when something waits), and `screen_idle` next to a blinking cursor.

## D-66 — The guest's proxy and the stream protocol of the net bridge (P4-T10)
- Status: Accepted (2026-10-13) · Type: Interpretation
- Context: PLAN §8 and §7.8: an HTTP proxy on 127.0.0.1:3128 handling `CONNECT` and absolute-form HTTP, each connection one smux stream to the host, which runs the egress policy; a refusal is a 403 with a reason a model can read; with no network, `403 Network is disabled for this session (start with --allow-net)`.
- Decision:
  1. **The proxy is part of the agent and always listens** on `127.0.0.1:3128` (IPv4 loopback, nothing else), whether or not the session has a network, so a program in a session without one gets a sentence it can use and not "connection refused". A client that is not on the loopback gets 403.
  2. **What it serves.** `CONNECT host:port` (a tunnel; bytes the client sent in the same packet as the request are the first bytes of the tunnel) and `GET/POST/... http://host/path` (forwarded through `httputil.ReverseProxy`, one connection for each request: `Connection: close`, no keep-alive, no response compression, `Proxy-*` headers not passed on, two minutes for the response header). Anything else is 400 with a sentence: the origin form, `https://` and other schemes in the request line, `CONNECT` without a port or with a port outside 1 to 65535. At most 128 connections at once (503 above that), 64 KiB of headers, 10 minutes of silence ends a connection.
  3. **The stream protocol** (`protocol.NetRequest`, `NetReply`): the guest opens a stream and writes one line of JSON `{"host":"example.com","port":443}`; the host answers one line, `{"ok":true}` or `{"ok":false,"error":"..."}`; after `ok` the stream carries the connection's bytes both ways. Lines are at most 1 KiB, decoded strictly (no unknown fields, one value), and read a byte at a time so nothing of the connection is consumed. The multiplexer is `xtaci/smux` v1.5.57 (MIT), protocol version 2 (a window for each stream, so one slow stream does not hold the others); both ends use `netproxy.MuxConfig()`. **A stream is only ever closed whole, never half-closed**: with `CloseWrite` on both sides smux v1.5.57 delivered an empty answer in about 3 % of exchanges (96 of 3000, with nothing but smux and a TCP socket pair in the test: the server wrote the answer and sent its end, and the opener, which had sent its own end first, read nothing), while data followed by a full `Close` lost nothing in 3000 exchanges and in 150 exchanges of 640 KB each way. The end of a direction is told over the TCP connection the browser or the server has, which does have a half-close; towards the host, the end of what the browser sent is a stream that is closed after the other direction has had its few seconds. The guest names, the host resolves: the guest never resolves a name.
  4. **Answers.** No port (the session has no network): `403` and the sentence from the plan. The host refused: `403` with `Denied: <its reason>`, cleaned to one line of at most 300 characters, and the same reason in the `X-ControlSnack-Reason` header. The port exists but the host does not answer, or the connection died: `502`, "The network bridge to the host is not connected"; the next request opens the port again (the session is dropped when it is found closed). The host has 30 seconds to answer a request for a connection; the request being canceled ends the wait at once. A tunnel is a `200 Connection Established` after the host accepts; a refusal is the `403` status line (browsers show their own error page for a failed `CONNECT`, not the body: a model learns the reason from `curl`, from the pages of plain http, and from the network status the system prompt states).
  5. **The tunnel** copies both ways; when one direction ends its destination is half-closed if it is a TCP connection (a stream is not, see above) and the other direction gets 3 seconds to finish, then both are closed. A client that half-closes its connection and waits for an answer therefore gets what the server says within those 3 seconds; browsers and curl do not do that. Silence for the idle time (10 minutes) closes it.
- Verified for real (guest without a network): the proxy listens on `127.0.0.1:3128` only; `curl` through it gets `403` with the sentence for http and "CONNECT tunnel failed, response 403" for https, and `400` when it is spoken to as a web server; the browser opens an http address and its page, as `read` returns it, is the sentence.
- Not verified for real: the multiplexing across a real virtio-serial port, which needs the host's bridge (P4-T11: tested with a fake host over a loopback socket until then).

## D-67 — The host's side of the net bridge (P4-T11)
- Status: Accepted (2026-10-13) · Type: Interpretation
- Context: PLAN §7.8 and §6.11: with `--allow-net` the guest asks for each connection over the second virtio-serial port; the host decides with the egress policy, resolves, connects and carries the bytes; limits are 32 streams, 5 minutes idle and 2 GiB for the session; every decision goes to the audit log as kind `net`. D-66 fixed the stream protocol.
- Decision:
  1. **`internal/netbridge.Bridge`** serves one multiplexed session (`smux.Server` with `protocol.NetMuxConfig()`, the same setting the guest uses; the setting moved to the protocol package so the two ends cannot drift apart). For each stream: read the request line (10 s), take a slot from `egress.Tracker`, call `Dialer.Dial` (`*egress.Policy` in production: it checks, resolves once, connects to the vetted addresses and checks again at connect), answer `{"ok":true}` or the reason, and carry the bytes. A refusal's reason is the policy's own sentence, cleaned to one line of at most 200 characters (and a generic "the connection was refused" if even that does not fit the 1 KiB line); an allowed destination that does not answer is refused with the dial error, and the audit record says `failed`, not `denied`.
  2. **A connection ends when either direction ends.** A stream has no half-close (D-66) and a stream whose peer has closed cannot be written to, so there is nothing to wait for in the other direction: the server's end of a finished answer is closed after its last byte (the guest sees the end after the last byte), and a guest that closed its stream cannot receive more, so the upstream connection is closed at once. **Idle is for the connection, not the direction**: a pump whose read times out goes on if the other direction moved within the idle time, so a download the guest does not answer is not cut at 5 minutes (a mutation that dropped this fails `TestBridgeDoesNotCallADownloadIdle`).
  3. **The byte budget is the session's**, charged for both directions as they are read (before they are written). When it is used up, the connection ends and new ones are refused with "the session's network byte budget is used up".
  4. **`Run`** keeps the bridge serving for the life of the session: it is given the connection Launch already made (QEMU waits for it before the guest starts) and a function that dials the port again (`Machine.DialNet`), and when a session ends (the guest's agent restarted, or the connection broke) it dials again after 500 ms. A failed dial is retried, not fatal; the context ends it.
  5. **Audit.** `Event` has two phases: `decision` (the policy's verdict, rule and reason; for an allowed destination also whether the server answered) and `closed` (bytes up and down and the duration). `Event.Record()` makes the `net` audit record: verdict `allowed`, `denied` or `failed`, the rule in `rules`, host, port and byte counts in `data`. The session (P7-T06) appends them; an `Append` fsyncs, so the callback blocks for the length of a flush, which is the price of an audit log that is on the disk before the bytes it describes have gone.
- Verified for real (`TestE2ENetBridge`, boot with `--allow-net`, under tcg in WSL): the multiplexer over a real virtio-serial port works, with several streams at once (Chromium opens a dozen) and a 457 KB download; **refused with their reasons** and nothing connected on the host (a listener on the host's loopback, on a port the policy allows, was never reached): `127.0.0.1`, `localhost`, `[::1]`, `10.0.2.2`, `192.168.1.1`, `169.254.169.254`, port 22, and an https `CONNECT` to `127.0.0.1`; a public page over plain http, over a `CONNECT` tunnel (curl, and by hand with the first bytes shown) and in the browser; and **the guest recovers when the host's end of the port is closed and opened again**: the first request after it gets `502 The network bridge to the host is not connected`, the next one goes through (3 s with a 2 s pause between).
- Found: (a) `curl -x` in the guest still skips the proxy for `localhost`, `127.0.0.1` and `::1` because the image sets `NO_PROXY` for them: the guest's own loopback is the guest's, which is right; the e2e test passes `--noproxy ''` to make the host see them. (b) `example.com` is blocked on this machine's network (an HTML page without a status line on port 80, a reset on 443; it is behind Cloudflare), which looked like a bridge defect until the host's side was traced: the e2e test now probes a few small public pages directly from the host and uses the first that answers as expected, and skips the public part if none does. `CS_E2E_TRACE=1` logs the first bytes of every connection the bridge makes. (c) the policy's reason for `::1` said "IPv4-compatible address" (it lies inside `::/96`); it now says "IPv6 loopback" (and "unspecified" for `::`).
- Not verified: the failure of a read or write on the guest's port while the host is not connected was seen only through its effect (the session closes, the next request opens the port again); deadlines on the port's `os.File` are not used (the multiplexer's keep-alive, 10 s and 30 s, ends a session whose host has vanished without an end of file).

## D-68 — Typing characters the keyboard lacks: a keycode for each, kept (P4-T13)
- Status: Accepted (2026-10-14) · Type: Interpretation (corrects the typing part of D-59)
- Context: D-59 types a character the keyboard does not have the way `xdotool type` does: one spare keycode is given the character (`ChangeKeyboardMapping`), pressed, and given back at the end of the request. The smoke test of the finished image typed `ControlSnack smoke test: ñ é 日本語` into Mousepad and read back `日語語`.
- Cause: an application looks a key event's keycode up in the server's mapping when it *handles* the event, not when the event was sent (GTK asks the server, `XGetKeyboardMapping`, at that moment). With one keycode remapped for each new character, a slow machine (tcg) or a busy application translates the press of 本 after the agent has already given the keycode to 語. The earlier test, which typed the same text into a terminal's title, passed by luck of timing.
- Decision: **a borrowed keycode keeps its character.** (1) Each distinct character gets a keycode of its own, from the keycodes with no keysym at all (`Keymap.Spares`), up to 64. (2) The mapping is not given back after the request: the keycodes belong to the connection (`lentKeys`, shared by the requests under `Conn.keyMu`), and a later request finds the character where it was left; the keyboard mapping read for that request already shows the character on that keycode, which `strokeFor` also finds as an ordinary key. (3) When all are taken, the keycode unused for the longest is taken over, and only after it has been unused for 2 seconds (`lentMinAge`): an application may still be about to look it up. A mapping that only grows is safe for a late look-up (a later state of the mapping has everything an earlier one had); only taking a keycode over is not.
- Consequences: no `MappingNotify` storm of one remap per character for text that repeats characters (a character already borrowed is not remapped again, in this request or the next); a long text of more than 64 distinct unusual characters waits 2 s per new character after the first 64 only if it is typed faster than that. The spare keycodes keep stale characters between requests; nothing else uses them (the VM has no physical keyboard).
- Verified: unit tests (a keycode for each character in order, the borrowed keycodes outliving a request, taking over the least recently used one only after the minimum age, a keycode idle long enough taken at once), mutation-checked (one keycode only, no minimum age, ignoring what an earlier request borrowed, newest instead of oldest); in the real guest the smoke test types the text into Mousepad, reads it back through the accessibility tree, and the screenshot shows 日本語.
- Supersedes / superseded by: amends D-59 (the single borrowed keycode given back after each request).

## D-71 — smux closes an accepted stream when its wrapper is garbage collected (P4-T13)
- Status: Accepted (2026-10-14) · Type: Interpretation (amends D-67)
- Context: the gate failed once, and then about once in a few hundred runs of a test under load, with `TestBridgeStopsWhenTheRequestIsCanceled` (the guest asks a host that never answers, and the request is canceled after 150 ms): the guest's request ended after 2 to 10 ms with an end of file, with nothing closed on either side of the connection.
- Cause (traced with the bytes of both ends of the connection, then a reproduction that failed or passed on one line): `smux.Session.AcceptStream` returns a wrapper with a finalizer that closes the stream when the wrapper is garbage collected (the finalizer of `OpenStream`'s wrapper was removed in smux, issue 997; the one of `AcceptStream` was not). The same line is in the fake host of the guest proxy's tests. The guest side only opens streams and is not affected. A test accepts a stream, keeps it as `defer st.Close()` does and runs the collector repeatedly: the guest's read must time out and not end (it ends with an end of file when the line is removed).
- Consequences: any code that accepts smux streams has to do the same (there is no other in the project); a handler does not need `runtime.KeepAlive`.

## D-72 — The tool schemas, the typed arguments and the validator (P5-T01)

  1. **The schema files are the description; Go is what the session uses.** `schema/tools/<tool>.json` (JSON Schema 2020-12, embedded in `schema.Tools`) holds the shape of each tool's arguments and, as `description`, what the model is told the tool is for; `schema/response.schema.json` is the JSON-mode envelope of the plan. `internal/llm/actions` has one argument struct for each tool (a field without `omitempty` is a required argument), a registry in the order of the envelope, and `Parse`. ## D-74 — Reading a model's reply: the parser and its repair messages (P5-T03)
- Status: Accepted (2026-10-14) · Type: Interpretation
- Context: PLAN §9.5: native tool calls, else a JSON envelope, else lenient extraction (a fenced block, else the first balanced object; trailing commas only); every action validated, all errors collected; no valid action means a repair message, at most two repairs per turn; more actions than the limit means the first ones run and the model is told the rest were dropped; words next to a tool call become the reason when there is none; reasoning blocks are stripped (§9.1).
- Decision:
  1. **Input and output.** `parse.Parse(set, Reply{Text, ToolCalls}, max)` takes what a backend adapter hands over (the words, and native calls with their arguments as a JSON object or, as OpenAI-compatible servers send them, a JSON string holding the object; empty or null means none) and returns a `Result`: the `Actions` to run (with the native call id, to send the result back under), the `Failures` (each an `*actions.Error` with every problem), `Skipped`, `Dropped`, the `Thought`, and the `Source` (native, json, none).
  2. **Reading a text.** Reasoning blocks go first (`<think>`, `<thinking>`, `<reasoning>`, `<thought>`; one that is never closed takes the rest of the text; a closing tag with no opening takes what is before it). Then the candidates in order: the whole text, each fenced block, each balanced `{...}` (string-aware, a mismatched closer is no match). The first that decodes and has a recognized shape wins: the envelope (`actions`), one action (an object with `tool`), or an array of actions. **The only mistake forgiven is a comma before a closing bracket**; unknown keys of the envelope or an action are ignored; `args` left out is `{}`, `args` as a string holding an object is that object. The `thought` of an envelope and any `reason` are cut to 600 and 300 characters, not refused (a note for the user is not worth a turn).
  3. **What runs.** The valid actions before the first invalid one, at most `max` (a limit that is not positive means three). An action may depend on the ones before it, so **the valid ones after a mistake are skipped, not run**; the plan's "no valid action means a repair message" is kept (`RepairMessage`, for a turn with nothing to run, naming every problem of every action and how to answer, for native calls or for JSON; at most `MaxRepairs` = 2 times per turn, which the session counts), and a batch that did run in part gets `Feedback` next to its results: what was not valid and why, how many were skipped, how many were beyond the limit. The actions beyond `max` are not even looked at.
  4. **The words of a model.** Text next to native calls is the thought and, as one clean line of at most 300 characters, the reason of the first action that has none. A reply with no action at all keeps its text as the thought and fails with "has no tool call and no JSON with actions in it".
  5. **Bounds.** At most 512 KiB of an answer is looked at, 32 candidates, and 256 braces are tried as the start of an object: a pile of 300 000 unclosed braces took 62 seconds when every brace scanned to the end of the text (found by a test), and takes milliseconds now; a real action after more than 256 braces of prose is not found (the model is asked to answer again).
- Verified: unit tests (native calls with object, stringified, empty and broken arguments; several calls, the limit, an invalid action in the middle, every failure reported; tools outside the profile; the words next to calls; the JSON answer as the whole text, in a fence, in prose, after braces that are not it, with trailing commas, after a reasoning block that holds JSON; the other shapes; the wrong answers; limits; answers with no action; the bounds; the extraction helpers; the repair and feedback texts, plural and singular, clean text); mutation-checked (reasoning kept, trailing commas not forgiven, actions run after a mistake, no limit, the words not used as the reason, stringified arguments not unwrapped); `FuzzParse` ran 30 s and 1.4 million inputs without a finding; `llm/parse` coverage 96 %.

## D-75 — The backend contract, the HTTP client and the Ollama client (P5-T04)
- Status: Accepted (2026-10-14) · Type: Interpretation (one addition: a limit on the length of an answer)
- Context: PLAN §9.1 gives three backends with the same job (`llm.Complete(ctx, prompt)` in §11) and a shared `httpx` with timeouts, retries and reasoning-block stripping; Ollama's native chat API with `num_ctx`, temperature 0, no streaming, `keep_alive`, images as base64, native tools or a `format` schema.
- Decision:
  1. **The contract** (`internal/llm/backend`): a `Request` is the messages (system, user with images, assistant with the native calls it made, tool results that name their call), the session's `actions.Set` and a `Mode`; a `Response` is a `parse.Reply` (the words and the native calls), the token counts the backend reports, the model's name, whether the answer was cut off by the limit on length, and the latency. The modes: `native` (the tools as functions), `structured` (the strict response schema of the set as the response format, for a backend that builds a grammar) and `json` (JSON asked for in the prompt, and in the request where there is a way). `Request.Validate` refuses what no API accepts (an image outside a user message, a tool result that follows nothing, a second system message, a call outside native mode, more than four images, a conversation that ends with the assistant); a bug of the caller is an ordinary error, a failure of the backend an `*Error`. The search for what a backend supports is the probe (P5-T07), not this contract.
  2. **The HTTP client** (`internal/llm/backend/httpx`): one deadline for each attempt, 600 s until a call has succeeded (it may be loading the model) and 180 s after; a call is made up to four times, with pauses of 1, 2 and 4 s, for what is worth repeating: 429, 5xx, a timeout, a connection that broke. **Not repeated**: a refused connection, a name that does not resolve, an untrusted certificate (nothing is there, and it says so at once), any other 4xx (400 and 422 mean the backend refused the request, and the probe knows another way to ask), and a 429 that asks to wait more than 30 s (the session pauses and says so, with the wait in the error). Failures are `*Error` with a Kind (`unavailable`, `timeout`, `rate_limited`, `server`, `auth`, `bad_request`, `not_found`, `protocol`), the status and what the backend said, cleaned to one line of at most 300 characters and with the key taken out; an error never holds a request body or a header. An answer larger than 64 MiB is refused. A context that ends stops the call, even while it waits to retry, and its error is the context's. `ValidateBaseURL` refuses an address with credentials, a query or a fragment (a key goes in a header, from the environment) and `IsLoopback` knows the names and addresses of this machine only by their form, never by resolving them. Reasoning blocks are stripped by the parser (D-74), not here.
  3. **Ollama** (`internal/llm/backend/ollama`): `POST {base}/api/chat` with `stream: false`, `options.num_ctx` (16384 unless told), `temperature: 0`, **`num_predict` 2048 (an addition: a model that does not stop would otherwise run for minutes; a cut-off answer is reported as `Truncated`)**, `keep_alive` 30m. Native mode sends the `ollama` rendering of the tools; structured mode the strict response schema as `format`; json mode `format: "json"`. Images go as base64 in the user message; an assistant message replays its calls with their arguments as objects (anything else becomes `{}`); a tool result carries `tool_name`. Ollama's calls have no id, so `call_<n>` is made up for the parser and the session. Ollama's own words about a missing model gain "pull it with: ollama pull <model>", and a refused connection says "is Ollama running?". A path prefix in the address (a reverse proxy) is kept.
- Verified: a fake Ollama (httptest) for the request (every field, the three modes, both profiles, the history), the answer (words, calls with and without ids, usage, truncation) and every failure (no model, no tools, an error in a good status, not JSON, no message, a server that fails and is retried, nothing listening, a canceled call); fixtures shaped like Ollama's real answers (timings, a thinking field, call indexes, a reasoning block and a fenced JSON with trailing commas in the content) read through the client and the parser to actions; the HTTP client against servers that fail, slow down, break, ask to wait, echo a key, send too much, or have a certificate no one trusts; the contract's validation; mutation-checked (streaming on, temperature, images, tool name, made-up ids, truncation, the strict schema); coverage 100 % (backend), 94 % (httpx), 96 % (ollama).
- Not verified: against a real Ollama (none is installed here): the exit of Phase 5 asks for `llm probe` against whatever local backend is there, and the first real model run decides whether `num_predict` 2048 and the 16384 window are right for the models people use.

## D-76 — The OpenAI-compatible client (P5-T05)
- Status: Accepted (2026-10-14) · Type: Interpretation
- Context: PLAN §9.1: `POST {base}/chat/completions` with the base address including `/v1`; native `tools` with `tool_choice: "auto"`, else a JSON-schema `response_format` if the server accepts it, else JSON in the prompt; images as `data:` URLs; tool results as `role: tool`, the next image in a new user message. LM Studio (`http://127.0.0.1:1234/v1`), llama.cpp (`http://127.0.0.1:8080/v1`), vLLM, OpenAI (`https://api.openai.com/v1`).
- Decision:
  1. **Request** (`internal/llm/backend/openai`): `stream: false`; `temperature: 0`, left out when `NoTemperature` is set (OpenAI's reasoning models refuse any value); the limit on the answer (2048 unless told) is `max_completion_tokens` for `api.openai.com` itself and `max_tokens` for every other server (the older name is the one local servers know). Native mode sends the `openai` rendering of the tools and `tool_choice: "auto"`. Structured mode sends `response_format: {type: json_schema, json_schema: {name: "controlsnack_response", strict: false, schema: <the strict envelope of the set>}}`. **JSON mode sends neither**: the servers do not agree on `json_object` (LM Studio refuses it), so the prompt alone asks. A key goes in `Authorization: Bearer` only when there is one (a local server wants none), and is taken out of every error text.
  2. **Messages**: a user message with pictures is a list of parts, the text and then each picture as `data:<type>;base64,...`; without pictures it is a string. An assistant message that only calls tools has `content: null`; its calls go back with their arguments as JSON text and an id (`call_<n>` when the call has none). A tool result carries `tool_call_id` (the call's id, or the tool's name when the id is unknown).
  3. **Answer**: the first choice. Its content may be a string, null, or (from a few servers) a list of text parts; its tool calls' arguments are passed to the parser as they came, text or object, an empty string meaning none (D-74). `finish_reason: length` is `Truncated`. An `error` in a good status is a refusal with its words; no choice is a protocol error. The errors of the HTTP client (D-75) gain the thing to do: a refused key says to check the environment variable named by `--api-key-env`, a refused connection says to check the server is running.

## D-77 — The Anthropic-compatible client, and every call answered (P5-T06)
- Status: Accepted (2026-10-14) · Type: Interpretation (amends D-75 for the contract's validation)
- Context: PLAN §9.1: `POST {base}/v1/messages` with `x-api-key` and `anthropic-version: 2023-06-01`; `tools` with `input_schema`; `tool_use` and `tool_result` blocks; base64 `image` blocks.
- Decision:
  1. **Messages** (`internal/llm/backend/anthropic`): the system message is the `system` field, not a message. A user message is its pictures (base64 `image` blocks) and then its words. An assistant message is its words and one `tool_use` block for each call (id, name, input as an object; anything else becomes `{}`). The results of native calls are `tool_result` blocks at the **start of the next user message**, and the observation that follows them goes into the same message after them: the API wants the roles to alternate and the results first, so consecutive tool and user messages of the conversation are merged into one. A result or a message with no words has the stand-in "(no text)" (the API refuses an empty block). The conversation must start with a user message (after the system one).
  2. **Request**: `max_tokens` is required (2048 unless told), `temperature: 0`, `stream: false`; native mode sends the `anthropic` rendering of the tools. This API has no response schema, so **structured mode asks in the prompt as JSON mode does** (no tools, no format). The key goes as `x-api-key` when there is one and is taken out of every error; the address may have a path prefix (a proxy).
  3. **Answer**: the text blocks joined by line breaks; each `tool_use` block a call, its input passed to the parser as the object it is; other block types (thinking, redacted thinking) are not read. `stop_reason: max_tokens` is `Truncated`; an `error` object in a good status, or something that is not a message, is a protocol error. HTTP errors are the client's (D-75): 529 overloaded and 5xx are retried, 429 waits for `Retry-After` up to 30 s, 401 says to check `--api-key-env`.
  4. **The contract now checks that every call is answered.** Anthropic refuses a conversation where a `tool_use` has no `tool_result` straight after it, OpenAI the same, and the session (P7) is the one that must answer each call the model made: with the result, with the reason it was not valid, with "not run" for the actions skipped after a mistake and "dropped" for those beyond the limit. `Request.Validate` refuses a conversation where an assistant message's calls are not each followed by a tool message, where there are more tool messages than calls, and where a user or assistant message comes before all are answered, so the bug shows up as a refused request in a test and not as a 400 from a provider on the first turn with a mistake in it.
- Verified: a fake server for the request (headers, every field, the system field, the roles alternating with results and observation merged and the results first, a picture before its words, stand-ins, no tools in the prompt modes, a path prefix, no key), the answer (words, calls, an unknown block type, usage, truncation) and every failure; fixtures shaped like Anthropic's answers (a thinking block, words and two tool_use blocks with cache counts; JSON in a fenced block; an answer cut by the limit; the four error bodies with their request ids) read through client and parser to actions; the validation of calls (five cases); mutation-checked (eight for the client, two for the validation); coverage 95 % (anthropic), 100 % (backend).
- Not verified: against the real API or a compatible server (no key and no server here).

## D-78 — Detection, the capability probe and its cache (P5-T07)
- Status: Accepted (2026-10-14) · Type: Interpretation
- Context: PLAN §9.2 and §9.3: `--llm auto` looks for Ollama and then LM Studio on this machine; `llm probe` tests vision, WebP, native tool calls and structured output on the chosen model; the result is cached; the session picks the best way the model can name its actions. D-75 to D-77 gave the three clients; nothing yet chose between them or between the modes.
- Decision (`internal/llm/detect`):
  1. **Finding the backend** (`Resolve`, `ResolveBackend`). With `auto` the candidates are asked in order, Ollama at `http://127.0.0.1:11434` (`/api/tags`) and then LM Studio at `http://127.0.0.1:1234/v1` (`/models`), 500 ms each, and **only a loopback address is ever tried**: a model that answers somewhere else is never chosen for the user, who has to name it (`--llm` and `--base-url`; a base address without `--llm` is a usage error because the protocol would be a guess). A named backend takes its default address or the given one; the address goes through `httpx.ValidateBaseURL` (no credentials, no query) and `Target.Local` says whether it is on this machine. The key is found by `config.ResolveAPIKey`, kept only in the `Target` and never printed, logged or cached. `Target.Notice()` is the sentence the terminal and the viewer say when the model is not on this machine (screenshots, screen text and command output are sent to it); the session audits it as `remote_llm` (P7).
  2. **Choosing the model** when `--model` is empty: the first that reports vision, **a loaded one first**; if none reports vision, the error lists the models found (at most 20) and says that a model without vision runs in text-only mode with `--model` (P5-T10).
  3. **Listing models** (`Models`): Ollama's `/api/tags` plus `/api/show` for each of the first 50 (capabilities `vision` and `tools`, the context length from `model_info`, the digest from the list); LM Studio's own `/api/v0/models` (type `vlm` is vision, `state: loaded`, capability `tool_use`, embedding models left out) and, if that is not there, the plain `/models`; any other OpenAI-compatible server gives names only (the probe finds out); Anthropic's `/v1/models` (every model sees and calls tools). What a server says is cleaned before it is printed.
  4. **The probe** (`Probe`) asks the model five small questions, one request each, none retried: **vision** (a 128×128 white picture with a red square, as PNG: "what colour is the square", answered as a JSON object, passes if the answer holds "red"); **webp** (the same picture as WebP, only if vision passed); **native tool calls** (the compact set, "call the done tool with success true", passes only if the reply has a real native call and it parses to `done` with `success: true`, so a model that writes the call as text does not pass); **structured** (the strict envelope of the set; skipped for Anthropic, which has no response schema); **json** (the answer asked for in the prompt, with the envelope given as an example). A backend that already says the model cannot see (Ollama's capabilities, LM Studio's type) is not sent a picture: the checks are recorded as skipped. The result is `Capabilities`: `Mode()` is the best way the model can name its actions (native, then structured, then json, none if all failed), `ImageFormat()` is WebP when the model read one and JPEG when it did not, `Vision` false means text-only mode.
  5. **What a failure means.** An error that says nothing about the model (the server cannot be reached, the key is refused, the model is not there, a timeout, a rate limit, the user stopped it) **ends the probe with that error and records nothing**; one the server answers with (a 400 for tools it does not support or for pictures, a 500, a wrong answer) is a capability the model does not have, with the reason as the check's detail.
  6. **The cache** keeps a result in `<cache dir>/probe/<hash>.json`, written atomically with mode 0600 in a 0700 directory, named by a hash of backend, address, model and digest (parts separated, so no two keys run together); it is used while it is under 14 days old, of the current `ProbeVersion`, and its own backend, address, model and digest match (the file is the user's, so its content is checked, not just its name); it is read at most 64 KiB; a result from the future is not believed. **A model that can do nothing is not cached** (a bad moment would keep a session from starting for two weeks), and a cache that cannot be written is ignored. The session uses the cache; **`llm probe` always asks again**. The API key is not part of the key or the content.
  7. **`controlsnack llm probe`** prints the backend and where it is (with the remote notice), the model, one line per check (ok, FAILED or skipped, how long, why), the context window, the screenshot format and the way actions are named, and exits 1 when the model can do none of them. **`controlsnack llm models`** prints a table (model, vision, tools, context, loaded; `?` for what the server does not say) and which model a session would use.
- Verified: fake Ollama, LM Studio, plain OpenAI-compatible and Anthropic servers on random ports (the request each probe question makes, headers, the picture kind that arrives); the order and the fallback of `auto`, a candidate off this machine never asked, a cancelled context, every refusal of a bad address; the model choice (loaded first, none sees, none offered, a long list); each list; a model that sees PNG but not WebP, one the backend says cannot see (no picture sent), one that does not see a picture and one whose server refuses pictures, native → structured → json fallbacks, tools written as text, nothing working; 401, 404, 429 and a gone server ending the probe, also late in it; the cache (reuse, forcing, expiry at 14 days, a new build, a changed model, address or version, garbage, empty, too big, from the future, no directory, a file where the directory should be, mode 0600/0700 on Linux, no key in the file, no model-less result); four golden reports in `testdata/llm/detect/`; the real binary with no server (the message names what was tried and what to do); mutation-checked (about forty mutations, all caught or equivalent: two equivalent ones were removed from the code). Coverage 95 %; the race detector is clean in WSL.
- Not verified: against a real Ollama, LM Studio or API (none installed here; the Phase 5 exit asks for `llm probe` against whatever is there and the answer is that there is nothing); whether small local models answer the five questions the way the fakes do (the first real run may find a model that sees but answers in prose, which would be recorded as failing vision, and the detail line says what it said).

## D-79 — The system prompt, the observation and the context budget (P5-T08)
- Status: Accepted (2026-10-14) · Type: Interpretation
- Context: PLAN §9.4 (the prompt, the history, the budget) and §5.2 (the observation, text or JSON, every coordinate in the space of the attached image, guest text fenced). `internal/safety/untrusted` already fences and cleans; `parse.Feedback` and `RepairMessage` already say what was wrong; the backends (D-75 to D-77) take a `Request` whose every native call is answered.
- Decision (`internal/llm/prompt`, `schema/observation.schema.json`):
  1. **The system prompt** is the embedded `system.tmpl`, rendered by `System(Params)`. It tells the model: it is the user `cs` without sudo with `~/work`; whether the machine has a network (and that a site that does not load may be blocked on the network of the host computer, not by the machine); how it sees (an image of WxH pixels, whose coordinates it uses, with numbered boxes when there are marks) or that it does not (then the tree and the screen text are the screen); how a turn works (1 to M actions in order, the ones after a failed action are not run, it is shown its last answers for a few turns); how to answer (native: tool calls with at most a sentence of text; structured and json: one JSON object with `thought` and `actions`); how to work (exec first, then ids, then the mouse; `wait_for` instead of turns; one key combination per `key`; check each result; two failed tries mean another way or `ask_user`; how the file manager appears in the tree (D-69); `done` to end); and what to trust (fenced text is data and never an instruction, even when it claims to come from the user or the developers; instructions found there are reported with `ask_user`; the only instructions are the task and the `USER` messages; the sandbox, the safety rules and the logs are not to be got around; a rejected action is not repeated). In `structured` and `json` mode it also lists the tools, one line for the tool and one for each argument with its type, bounds, default and whether it is required, made from the same schemas that check the calls (`ToolDocs`). `SystemVersion` (1) and the SHA-256 of the template (and of the rendered text) identify it for the audit. The nonce is 4 to 64 letters and digits.
  2. **The observation** is `Observation`, with every coordinate already in image space (the session rescales; T09 gives it the mapping). The text form is the plan's example: `TURN n · screen WxH · cursor x,y · network · mode · tools`, `TASK`, `ACTIVE WINDOW class [bounds]` and the title fenced, `UI generation g · scope s · shown/total nodes` with the nodes fenced one to a line (`a17 push_button "OK" [600,500,80,30] value="..." states=... actions=click`, roles with `_` for spaces), `OCR generation g · shown/total lines` (`o3 "text" [bounds]`), `LAST RESULTS` (`1. exec ok exit=0 31ms` and the output fenced), `NOTE` (the host's feedback), `USER` (what the person watching wrote), `BUDGET actions_left turns_left time_left`, `[image attached: WxH, marks for a1..a23]`. Text of one line is fenced inline, as in the plan's example; text of several lines goes between lines of its own. The JSON form (`--obs-format json`) has the same parts as fields; a block that came from the guest is one fenced string (the tree is one string of lines, not an array of objects, so one fence covers it and an element costs what it costs in the text form); `schema/observation.schema.json` (strict: no other fields) describes it and the tests validate what is rendered against it.
  3. **What the guest cannot do to it.** Strings the guest chooses are in a fence, cleaned and with `<<` broken by `untrusted.Fence`; what stands outside a fence is a number, a token (letters, digits, `_ - . :`, cut short: class, ids, roles, states, actions, generation, scope, tool names, error codes, mode words), the host's words about a result (`Detail`, cleaned **and then** sanitized: sanitizing first and cleaning after joined two `<` that had a bad byte between them, which the fuzz target found), notes (sanitized the same way), or the user's own text. The task and the user's messages keep their `<<` (a task can be a shell here-document) but their lines after the first are indented by two spaces, so that a line in them cannot pass for a section such as `BUDGET`. The tests render a hostile string in every place and check that the fences are balanced and not interleaved, that no `<<` is left outside them, and that every line outside a fence is one of the forms the renderer writes; a fuzz target does the same (290,000 inputs, one bug found and fixed).
  4. **The conversation** (`Conversation`): `Begin(obs, image)` starts a turn (the previous turn loses its picture; only the current one has one); `Assistant(text, calls)` records the model's answer (reasoning blocks stripped, 3000 characters at most); `Results(results, limits)` records what came of the actions. With **native** calls it appends one tool message for each call in order and refuses a number of results other than the number of calls, or a result for another tool than the call, so that no call is left unanswered (the session supplies a result for the invalid, not-run and dropped actions too); with any other mode the results wait for the next `Begin` and are shown in that observation. `Note` and `UserMessage` queue text for the next observation; `Notice` speaks now (the repair message, after the tool messages of the same turn). A turn that is not the current one is shown in its compact form: its header, active window and results, without the task, tree, screen text and picture. The last six turns before the current one are kept (`DefaultKeepTurns`); older ones become one line each (`Turn 3: exec {"command":"ls"} -> ok; click_element {...} -> error stale_element`, 240 characters at most, the last 30 listed), put at the start of the first message that follows; a turn that can never be shown in full again gives up its messages.
  5. **The budget.** Tokens are estimated: a quarter of the bytes of ASCII plus one for every other character, 4 for each message, and the picture by backend (Anthropic width×height/750 up to 1600, OpenAI 85 + 170 per 512-pixel tile after its documented scaling, local models one for each 28-pixel patch between 600 and 2400). The fixed part is the system prompt and what the backend is sent besides the messages (the tool definitions of native mode, the strict envelope of structured mode). `Request` stays under **85 %** of the context (`ContextTokens`, 16384 when unknown) and gives up, in the plan's order: past turns one at a time (oldest first, down to none), then the nodes of the current tree (halved down to 8; those with actions, a state that matters or inside the active window are kept, in the order of the tree), then the lines of screen text (halved down to 5), then the text of results (halved from 16 KiB down to 256 bytes); if that is not enough it returns a `ContextError` that says what to do (more context, `--num-ctx`, another model, a shorter task). The `Report` says what was kept and cut, for the log and the viewer. The request is validated before it is returned, so a conversation a provider would refuse is found here.
- Verified: golden files for three system prompts (native with marks, json text-only with a network list, structured full) and for the observation in both forms and two conversations; the observation of the plan; every node form; hostile strings in every field, in text and JSON, plus the fuzz target; the schema accepts what is rendered and refuses six malformed documents; the budget over 150 windows from 1,500 to 40,000 tokens (things are given up in the order turns, nodes, screen text, results, error; the estimate is never over the limit) and 300 random conversations (always valid, always within the limit, never two pictures); `Results` refuses a missing result and another tool's result; about fifty mutations, all caught or equivalent (one was: a restatement in `nodeLine`, removed from the code). Coverage 97 %.

## D-80 — The picture the model sees, and where it points (P5-T09)
- Status: Accepted (2026-10-14) · Type: Interpretation (amends the screenshot response of D-59/the protocol of PLAN §5.1 with one field)
- Context: PLAN §9.3: ask the agent for images at most `llm.image_max` on the long edge, keep the scale factors, map `mouse`, `scroll` and `region` coordinates back with `gx = round(x * guestW / imgW)`, clamp an overshoot of up to 2 %, otherwise `invalid_args`; set-of-marks per D-30 (on for local models with vision); the format per the probe; only the latest picture stays in context. The agent already scales (`max_long_edge`) and draws marks (`marks_generation`); what was missing is the host's half.
- Decision (`internal/llm/vision`):
  1. **The mapper.** `Mapper` knows the guest size and the picture size. Going to the picture (what the model reads: bounds of windows, elements and text lines, the cursor) a rectangle is converted by its two corners and the size is what lies between them, so two elements that touch on the screen still touch in the picture; a rectangle that is not empty keeps at least one pixel (and may then overlap its neighbor by that pixel); the cursor is kept on the picture. Coming back (what the model says) a position is `round(v * guest / picture)`. All rounding is integer arithmetic, half away from zero, so it is the same on every platform. A region is converted by its corners; its far corner may be the size of the picture; the result is a non-empty part of the screen.
  2. **The 2 % rule.** A coordinate up to 2 % of the picture's size beyond either edge is taken as the edge pixel (clamped before it is scaled: 641 on a picture 640 wide is pixel 639, whatever pixel 641 would scale to); further out is a `*RangeError` whose words say what is valid: `to_x=2000 is outside the screenshot, which is 1280 pixels wide (use 0 to 1279)`. A picture too small to have a whole pixel of overshoot (under 50 pixels) allows none. A coordinate is also never past the last pixel of the screen, whatever the sizes (the mapper does not rely on the picture being the smaller one).
  3. **Actions.** `Mapper.Guest(action)` returns a copy of a `mouse` (x, y, to_x, to_y), `scroll` (x, y) or `read_screen_text` (region) action with its coordinates in guest pixels; the action given, and its `Raw` arguments (what the audit log shows: what the model said), are not changed; any other action is returned as it is. An out-of-range coordinate makes the action `invalid_args` with one problem for each coordinate (`args.x`, `args.to_y`, `args.region`), so the model can put them all right at once. In text-only mode the mapper is the identity (the model says screen pixels) and still checks the range.
  4. **The pipeline.** `Pipeline.Capture(ctx, generation)` sends `screenshot` with the format of the probe (`Capabilities.ImageFormat()`), the quality, `max_long_edge` = `llm.image_max`, and, when marks are on and a generation of the tree is given, `marks_generation`; otherwise `if_changed_since` the hash of the last plain picture, and a screen that has not changed returns that picture again (`Shot.Reused`) with the new cursor. A picture with boxes is never the shortcut and is not remembered as the screen. What the agent says is checked as anything from the guest is: the blob is there, the format is the one asked for, the header of the picture (`imaging.Inspect`: format, size, at most 4096) agrees with the response, the scale is in (0, 1] and the size agrees with the guest screen at that scale (to a pixel), the fingerprint is hexadecimal and short, the ids of the marks look like `a12`/`w3`, are not repeated, are not more than 100 and are only there when marks were asked for. A `Shot` carries the `backend.Image`, the `prompt.ImageNote` (size and the range of the marks), the `Mapper`, the cursor in picture pixels, the hash and the ids marked.
  5. **The agent says which boxes are on the picture.** `ScreenshotRes` gains `Marked []string`: the ids of the elements whose boxes were drawn (`imaging.Drawn` is the question `DrawMarks` asks about which marks fit, now shared), in the order of their numbers. The host needs it for the line `[image attached: 1280x800, marks for a1..a23]`, which names the first and last ids drawn (those in between that have no box are not operable). One field, optional, added to the embedded agent.
  6. **Marks on or off.** `MarksEnabled(setting, local, vision)`: `on` is on when there are pictures, `auto` is on for a local model with vision (D-30), `off` never; in text-only mode never. The system prompt now says what a box number means: the box numbered 17 is the element a17, which `click_element` takes by id.
  7. **Conversions.** `Mapper.Window`, `UITree`, `Nodes` and `OCR` turn the protocol's answers into the `prompt` types of D-79 with their coordinates in the picture's pixels, so the session builds an observation without arithmetic of its own.
- Verified: the mapper over seven screen and picture sizes (every screen pixel goes to a picture pixel and back within one picture pixel; every picture pixel is on the screen; neighbors still touch; the rounding of negatives; the 2 % rule at both ends and at its limits on both axes; regions at the edges and past them; 2,000 random regions are all real parts of the screen); the rewriting of every coordinate-bearing action, that the action given is not changed, that the other actions are not, and a problem for each coordinate that is out; the pipeline against a fake agent (the request in each configuration; unchanged screens; marked pictures; fourteen kinds of hostile answer; seven kinds of bad mark ids; every format); and **against the agent's own screenshot handler** on a 1920×1080 display with colored blocks at four picture sizes (the bounds that the mapper gives for a block are where the block is in the picture, to two pixels; a click at the middle of the block as it appears in the picture lands on the block on the screen; the boxes named are the ones drawn). ## D-85 — The viewer's door: what the server checks, in which order, and what it reports (P6-T01)
- Status: Accepted (2026-10-17) · Type: Interpretation (fills in PLAN §10.1)
- Context: the viewer is a web server on the user's own machine. Anything that runs there can connect to a loopback port, and a web page in the user's browser can make requests to one too, so the server is the door of the program: it can show the screen of the VM, take chat and approvals, and fire the kill switch.
- Decision (`internal/viewer`, `web/`):
  1. **Listener and Host.** `Server.Start` listens through `platform.ListenLoopback` (127.0.0.1, a free port). Every request, before any route, must carry `Host: 127.0.0.1:<port>` exactly (no `localhost`, no trailing dot, no other name), else 403: a name that resolves to this port from a page somewhere else (DNS rebinding) is never served. The check also applies to `/control/kill`, which `controlsnack kill` reaches at that very address.
  2. **Login.** `AuthURL()` makes a link `http://127.0.0.1:<port>/auth?t=<64 hex>`; the token is 32 random bytes, kept only as a SHA-256 digest, good once, for 60 s (`Options.BootstrapTTL`), at most 16 waiting at once. `GET /auth` (only GET: a HEAD would use it up) answers 303 to `/` with the cookie `cs_session` (32 random bytes, `HttpOnly`, `SameSite=Strict`, `Path=/`, no expiry, so it dies with the window). A link that is unknown or expired is 401. **Tripwire:** a link that was already used, used again, is 403, fires the kill switch (`SourceInternal`, "the viewer's login link was used twice") and reports `viewer_tripwire`: the link was in a command line and a URL, and a second user of it is another process (or the first one racing it). An expired link that was never used is not a tripwire. A window that logs in over another replaces the cookie: the old one is out, and its socket is ended.
  3. **What needs the cookie.** Everything but `/auth` and `/control/kill`: the page, its script and style, `/ws`, `/api/kill`. The cookie is compared in constant time (`secret.Equal`).
  4. **The socket gate.** `GET /ws` needs the cookie, an `Origin` header that is exactly the viewer's origin (required, one value), a `Sec-Fetch-Site` of `same-origin` when the browser sends one, and a free slot: one live connection, a second is 409. The handler (P6-T02) is given a context that ends when the connection's window is replaced or the server closes. A reload that reconnects at once can meet the slot still held for a moment: the page retries.
  5. **The kill button without a socket.** `POST /api/kill` needs the cookie, the CSRF value (32 random bytes, in `X-CS-CSRF`; `Server.CSRF()` goes into the hello message), an `Origin` that is the viewer's when the request has one, and `Sec-Fetch-Site: same-origin` when sent. It fires the kill switch (`SourceAPI`) and answers when QEMU is gone, or after 800 ms, like the CLI's endpoint. `POST /control/kill` is `killswitch.ControlHandler` (bearer kill token, no cookie).
  6. **Headers.** On every answer, errors included: the CSP of §10.1 with the actual port in `connect-src`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, both `Cross-Origin-*` policies `same-origin`, `Cache-Control: no-store`. No CORS header is ever sent.
  7. **Static files.** Only what `Options.Static` (the embedded `web/static`) holds and only the kinds in a fixed table (`.html .js .css .svg .png .ico .json .woff2`, with their types: the operating system's table, the Windows registry's, may call a script plain text). A name is cleaned by `fs.ValidPath` before it is read; directories, other kinds and `..` are 404. `GET` and `HEAD` only, else 405 with `Allow`.
  8. **What the session hears.** `Options.Event` receives `viewer_auth`, `viewer_auth_denied`, `viewer_tripwire` and `viewer_refused` (Host, Origin, cookie, CSRF, a second connection) with one clean line each, never a token, a cookie or anything the other side sent. Refusals and denials are limited to one of each kind per second, with the count of those left out (`Suppressed`): another process that hammers the door must not fill the audit log, and a log that cannot be written ends the session.
  9. **Server limits.** Header timeout 5 s, idle 60 s, headers at most 16 KiB, no log of its own. No `WriteTimeout`: the socket writes long-lived frames and bounds each write itself (P6-T02).

## D-86 — The viewer's WebSocket: messages, one connection, a page that cannot slow the session (P6-T02)
- Status: Accepted (2026-10-18) · Type: Interpretation (fills in PLAN §5.4), with one addition: the `pong` message and the optional `src` of a kill
- Context: the session produces frames, traces, chat and state at the speed of the VM and the model; the page may be on a slow machine, in a background tab, or gone. Nothing the page does, or fails to do, may hold up the session loop or the kill switch. Everything the page sends comes from a process that could be hostile (anything that can read the cookie), and everything the host sends contains text from the machine and the model.
- Decision (`internal/viewer`: `protocol.go`, `client.go`, `hub.go`, `conn.go`; `schema/viewer-ws.schema.json`; library `github.com/coder/websocket` v1.8.15, ISC):
  1. **The messages** are the structs of `protocol.go`, one per kind of §5.4, written as `{"type":..., ...}` by `Encode` (the type first). `schema/viewer-ws.schema.json` is the contract for the page and for the tests (`server_message`, `client_message`, `additionalProperties: false` on every one); every message the host makes is validated against it in a test. A message over 256 KiB is not sent: the page gets a `notice` saying one of that type was too large. A trace or confirmation with no rules or no arguments is written with `[]` and `{}`, never `null`. The only additions to §5.4: **`pong {t}`** (the answer to `ping`) and the optional **`src`** (`button` or `hotkey`) of a `kill` control, so that the kill switch's audit record says what was pressed (D-19). Frames are binary: `0x01`, `uint32` sequence, `uint16` width, `uint16` height (all big-endian), WebP bytes; at most 4 MiB.
  2. **The host never waits for the page.** `Hub.Send` and `Hub.SendFrame` only put bytes in a per-connection queue. Messages are of three kinds: *essential* (state, trace, chat, confirmations, notices, ended) are kept in order and, when 256 are waiting, the page is cut off (it reconnects and is shown the snapshot below); *droppable* (audit lines, plans, pongs) are left out when 128 are waiting; *latest* (cursor, stats, frames) keep only the newest, so a page that is behind sees the present and not a queue of the past. The writer takes the ordered messages first, then the newest cursor, stats and frame. Each write has a 10 s timeout; a ping every 20 s (answered only by a page that reads) finds a page that vanished. A page that is stalled is dropped with `CloseNow` (it would not answer a close frame either, and waiting would hold the session's one slot); every other end uses the closing handshake with a status the page can read: 1001 when a window logs in over this one or the viewer closes, 1003 for a binary message, 1008 for too many messages that break the rules, 1009 over the limit of 64 KiB.
  3. **Reconnecting is cheap.** The hub keeps what a page that connects later should see and sends it after the `hello`, in this order, before anything live and with no gap or repeat (the snapshot and the connection are made under one lock): the last `state`, the last 200 audit lines, the last 200 chat, trace and notice messages (at most 2 MiB of each), every confirmation request that is still open (an open one is never lost by a reload, however many messages came after it), the last cursor, the `ended` message if there is one, and the last frame.
  4. **What the page sends is checked as if hostile** (`ParseClient`). A text message of at most 64 KiB that is one JSON object with no other value after it, of a known `type`, with exactly the fields of the schema (no others, none missing, of the right kind): `chat` (1 to 8000 characters after trimming; valid UTF-8; no control characters other than line breaks and tabs, none of C1, no DEL), `confirm` (`id` of `[A-Za-z0-9_.:-]{1,64}`, `approve` present and boolean, a note of at most 500 characters), `control` (`pause`, `resume`, `stop`, `kill`, `step_on`, `step_off`; `src` only with `kill`), `ping` (a finite number `t`). A type that is not one the page sends is dropped and counted; a known type that breaks the rules is dropped and counted, and after 50 of them the connection is closed (1008); a binary message closes it (1003). Messages are limited to 10 a second with a burst of 10; the rest are left out, and the page is told once in five seconds. **The kill is never limited**: it fires the kill switch (`SourceButton` or `SourceHotkey`) from the reading goroutine itself, and the session is not asked.
  5. **The session's side** is two small interfaces: `Inbound` (`Chat`, `Confirm`, `Control`; they run on the reading goroutine and must not block, so the session queues the request) and the callbacks `OnConnect` and `OnDisconnect` (the frame pump of P6-T03 and the dead-man timer of P6-T08 hang on them). The hello message is made by the session at each connection (`HubOptions.Hello`); the hub adds `proto` and the CSRF value.
  6. **Library details that mattered**: coder/websocket drops a connection without a close frame when the context of a read or write ends, so the reads and writes use their own contexts and a separate goroutine closes the connection (orderly, or at once) when the connection's context ends; compression is off (the frames are already WebP, and a decompression bomb is not a risk to take); the library's own origin check also runs (the server has already required exactly the viewer's origin).
- Verified: against the real server and a real WebSocket client: the hello and the replay in order (and that a plan, stale stats and a resolved confirmation are not replayed), every kind of message against the schema and the schema against 25 bad messages, what the person does reaching the session (trimmed, in order), kill with each source, a flood of 60 chat messages (5 to 9 got through, one notice, the kill still worked), 12 kinds of bad message dropped with exact counts and the cut-off after 50, binary and oversize messages, ping and pong, one callback pair per connection, a window logging in over another (1001), an oversized message turned into a notice, a page that never reads (300 rounds of 250 KB messages, cursors, audit lines and frames: the session is not held up, the page is cut off), a page that does not answer pings, bounded history with an open confirmation kept; the queue's rules without a network (order, newest-only, droppable limit, overflow, waiting and ending); a fuzz target for `ParseClient` (1.7 M executions, no failure) with the invariants of every accepted message; frames and `Encode`. Coverage 97.5 % of `internal/viewer` (the new tests lifted it past 97 %). Mutation checks: 35 changes that each turn off one rule above (strict fields, id and text limits, trailing data, the kill source, the limiter and its exemption for the kill, binary messages, the cut-off after 50, the queue limits, newest-only slots, the abrupt close, the detach, each part of the replay, the confirmation bookkeeping, the type field, the size limit, null rules) each make a test fail; one survived at first (a resolved confirmation kept in the map, hidden by the order list) and now has its own test. Race detector clean in WSL (3 runs).

## D-87 — The frame pump: what is asked of the guest, what is forwarded, and the budgets (P6-T03)
- Status: Accepted (2026-10-18) · Type: Interpretation (fills in PLAN §10.3)
- Context: the page needs the screen, and the screen costs the guest (a screenshot under tcg takes tens of milliseconds to encode, D-57) and the pipe between the guest and the host. It must be there when someone watches and cost nothing when nobody does, and what a hostile guest puts in a picture must not reach the browser's decoder unchecked.
- Decision (`internal/viewer/pump.go`; `Hub.Stats().BytesSent`):
  1. **Only while a page is connected.** `Pump.OnConnect` and `OnDisconnect` are the `HubOptions` callbacks; the first starts one loop on its own goroutine, the second stops it and waits for it. A second connect event starts nothing. The loop never touches the session: what the session tells the pump (`Activity`, `NoteAction`, `NoteLLM`) is an atomic store or a signal in a channel of one place.
  2. **The rate.** 5 looks a second during an action and for 3 s after it (`Activity` is called when an action starts and ends), 2 a second otherwise; an activity that arrives while the pump waits brings the next look forward to one active interval after the last, not to the end of the idle wait. Each look is scheduled from the start of the last one, so a slow screenshot makes the next come at once and never a burst. The first look is at once.
  3. **What is asked and sent.** `screenshot{webp, q70, if_changed_since: <hash of the last picture sent>}`, full size. An `unchanged` answer sends no picture. A picture is forwarded only after `imaging.Inspect` has read its header and found the declared format and size and at most 4096 pixels a side (the open item of the earlier phases: a guest that lies about a picture cannot make the browser's decoder allocate more than the header says); a picture that fails is not forwarded and not remembered as the last. The sequence number rises for each picture offered to the hub, so the page can see a gap.
  4. **The cursor** comes with every answer, changed picture or not. It is sent when it differs from the last one sent and at least 100 ms after it (at most ten a second); a move that has to wait is sent by the next look, which compares with the last one that went.
  5. **Failures.** A look that fails (the agent is down, a picture that is refused, a frame the hub cannot send) is reported through `OnError(err, inARow)` and the pump goes on at half the rate, then a quarter, up to one look in 2 s; an activity during an outage does not shorten the wait. The first look that works sets the rate back. The session decides what to tell the person (the "agent offline" state of §10.2 is its call).
  6. **Stats** every 2 s from the pump's own counts and the hub's: `kbps` is KB (1024 bytes) a second written to the page, of frames and messages together, over the window; `fps` the pictures sent in it; `frame_bytes` the last picture's size; `llm_ms` and `actions` as the session reported them. Rounded to a tenth.
  7. **Testable time.** The pump's clock is an interface (`Clock`: `Now` and a `Wait` that returns early for a wake signal); the tests move a pretend clock, so a minute of the pump's life takes a few milliseconds and its timing is checked to the millisecond.
- Budgets (PLAN §10.3), as tests: an idle minute of a desktop that changes once in ten seconds, with 1080p pictures of 48.7 KB, averages **4.9 KB/s** against the limit of 50 (6 pictures, 120 looks); synthetic 1080p pictures at q70 are 5.2 KB (bare), 35 KB (a window) and 48.7 KB (three windows with text), against 200 KB. The real guest gave 8 KB for a bare desktop and 47.6 to 55.9 KB for a terminal and a file manager (D-57), so the synthetic scenes are in the same range. **The idle budget depends on the screen being still**: a screen that changed at every idle look would send two pictures a second, about 100 KB/s; a video or an animation is outside it. A cap on the bytes a second (a lower rate for a screen that never stops changing) is not built; it is in the TODO.
- Verified: idle cadence to the millisecond over 10 s, the active window of exactly 3 s (4, 15 and 10 looks in the three stretches), an activity during a wait, only changed pictures sent and the request that names the last picture, four kinds of picture a guest might send that are refused, an outage's schedule (0, 1, 3, 5, 7, 9 s) and that activity does not cut it short, a frame the hub refuses, the cursor at 50 looks a second (at most 10 messages in any second, the last position always arrives, no repeats), the figures of the stats, the connection's start and stop with the real clock, and the pump in front of the real hub and a real WebSocket client. Mutation checks: 26 changes that each turn off one rule (each default rate, the active check, the question about the last picture, the header inspection, remembering the picture, sending unchanged ones, the cursor gap and the repeat check, the rounding, the stats window, the backoff and its cap and its reset, the wake-up, the action count, the model time, a second connect, waiting at disconnect, the hub's byte count) each make a test fail; one survived at first (disconnect not waiting) and has its own test now. Race detector clean in WSL (3 runs).
- Not in this task: the page that draws the frames (P6-T04); the session that calls `Activity`, `NoteAction` and `NoteLLM` and reports `OnError` (P7); the "agent offline" fallback through QMP (§10.2, P7).

## D-89 — The approval dialog: a refusal is easy, an approval is deliberate, and Kill is always in reach (P6-T05)
- Status: Accepted (2026-10-18) · Type: Interpretation (fills in PLAN §10.2 "Confirmation modal"), with one addition to the protocol: `hello.now`
- Context: the dialog is where the safety rules hand a decision to the person. Two mistakes are possible and they are not equal: an approval the person did not mean (a click meant for something else, a script, a habit of pressing Enter), and a dialog that blocks the person from stopping everything. The page also has no way to know the host's clock, so a countdown can be wrong by hours.
- Decision (`web/static/confirm.js`, wired in `app.js`; `hello.now` in `internal/viewer/conn.go` and the schema):
  1. **What it shows.** The tool, the model's reason, every rule that matched with its explanation, the action's arguments as pretty JSON, a field for a note for the log (up to 500 characters), and a countdown. Everything is text (`textContent`); the arguments are cut at 6000 characters with the count that was left out. It is a `role="alertdialog"` with a label and a description, so a screen reader announces it.
  2. **Reject is the default.** It has the focus when the dialog opens; **Esc rejects**; Enter on the focused button rejects. It is the primary button. The Esc that rejects is stopped (`stopPropagation`), so that it cannot be counted as one of the three Esc presses that kill (P6-T07 must ignore a key event whose default was prevented).
  3. **Approve is deliberate.** Only a click that is trusted (made by the person's input, not by a script: `event.isTrusted`) answers, for Approve and Reject alike; Approve does nothing for its first 700 ms (`aria-disabled`, and the click is ignored), so a dialog that appears under the pointer cannot take a click meant for what was there. There is no key that approves: Enter on Approve is possible only after the person has tabbed to it. Clicking the backdrop does nothing.
  4. **Several requests are asked one at a time**, in the order they came ("Request 1 of 3 waiting"). When the host ends one (`confirm_resolved`: the person answered elsewhere, it expired, it was canceled), the next one comes up; an expiry or cancellation of a request this page did not answer is reported as a notice, an outcome the person just chose is not.
  5. **The answer is not final until the host says so.** After an answer the buttons are held ("Sent. Waiting for the host…") and the dialog stays until `confirm_resolved`; if nothing comes in 6 s the buttons come back and the person can answer again. A page that is not connected says so and keeps the dialog.
  6. **Kill stays in reach.** The rest of the page (`main`) is made `inert` (no click, no focus, hidden from assistive technology) while a dialog is open, but the header, with the Kill button, is above the backdrop and is part of the Tab cycle (the dialog makes the cycle itself, note, Reject, Approve, Kill, in both directions: the Kill button is early in the page and the dialog late, so the browser's order would have left the dialog). The focus goes back to what had it when the last dialog closes.
  7. **Nothing is left over.** The queue is emptied when the page connects again (the host replays what is still open, so a reload shows an open request once), when the connection drops, and when the session ends or is killed.
  8. **The countdown uses the host's clock.** `hello.now` (the host's time when the page connected, RFC 3339) gives the difference between the two clocks; `expires_at` is read through it. At zero the page says time is up and waits for the host, which decides.
- Verified in a real browser (D-88's rig): the content of the dialog (title, reason, both rules, the arguments, a countdown that can be right only with the clock correction, the position), Reject focused, the page behind inert and Kill enabled, Esc rejecting and the dialog staying until the host answers, a script's clicks ignored for both buttons, a real click on Approve after the pause with the note, Enter rejecting, the pause itself (a copy of the dialog with a minute's pause and one with none), three requests asked in order with the expiry notice, a reload (one dialog), Kill with the dialog open, the Tab cycle forward and back, the dialog gone when the session ends, the answer the host never takes (buttons back after 6 s), and the contrast of 13 kinds of text in the dialog in each scheme (lowest 6.96 dark, 5.77 light). Mutation checks: 22 changes that each break one thing (Esc, the focus on Reject, a script's click on either button, the pause, the Tab cycle, the inert page and lifting it, the host's clock, the expiry notice, the position, holding the answer, the second chance, giving the focus back, showing the rules, the arguments, the reason, the note, clearing at the end, computing the skew, the host's clock in `hello`) each make a test fail; two survived at first (a script's click on Approve, hidden by the pause; the focus given back) and have their own tests now.
- Not in this task: the session side (P7: `Inbound.Confirm` must answer `confirm_resolved`, with `expired` when its own timeout fires, and must ignore an id it does not know), and the hotkeys (P6-T07).

## D-90 — Rendering-safety checks in the gate (P6-T06)
- Status: Accepted (2026-10-18) · Type: Interpretation (fills in PLAN §10.1 "no inline scripts or handlers (CI grep check, P6-T06)" and Phase 6 T06)
- Context: the viewer's safety does not rest on the page being careful. The content security policy refuses inline code and styles, and the page sets every host string with `textContent`. But a later change could build markup from a string "just this once", reach for a library on a CDN, or keep the CSRF value in local storage, and the policy would not always notice. The tests of D-88 and D-89 show that the page as it is behaves; this keeps what it is made of from drifting.
- Decision (`tools/dev/webchecks.go`, run by the `repo` step of `go run ./tools/dev check`, so the gate and CI refuse it):

## D-91 — The kill hotkeys: which key presses count (P6-T07)
- Status: Accepted (2026-10-18) · Type: Interpretation (fills in PLAN §10.5 and D-19)
- Context: D-19 gave two keyboard ways to kill: Ctrl+Shift+Esc "where the OS delivers it to the page" (Windows keeps it for Task Manager) and Esc three times within 1.2 s. Esc is also what closes an approval dialog (D-89), cancels an IME composition, and repeats when held. A kill that can fire from any of those would be a way to lose a session by accident; one that cannot fire when the person means it would be worse.
- Decision (`web/static/hotkeys.js`, listened to on `window` by `app.js`):
  1. **The combination**: Ctrl+Shift+Esc, with no Alt or Meta, kills at once. Any other combination with a modifier never counts or kills (Shift+Esc, Ctrl+Esc, Alt+Esc, Meta+Esc, Ctrl+Shift+Alt+Esc).
  2. **The sequence**: the last three plain Esc presses, counted from the event's own `timeStamp`, kill when the third is at most 1200 ms after the first (a window that slides: presses at 0, 600 and 1300 ms do not kill, and a fourth at 1400 ms does, because 600, 1300 and 1400 are close enough). After any kill the count starts over.
  3. **What never counts**: a press whose event is not trusted (made by a script), one whose default was prevented (the approval dialog's Esc, which also stops the event from reaching the window, so two things have to go wrong for it to count), one that is part of an IME composition, one that is a held key repeating, and any other key.
  4. **Feedback**: after the first and second press of a sequence a red hint in the header says how many more presses kill ("Press Esc 2 more times to kill the session."), and clears after 1.2 s; the kill button's tooltip names both ways. The person is never surprised by the third press, and a first Esc that was meant for something else is visible.
  5. **The kill itself** is the page's `kill("hotkey")`: the socket (`control kill`, `src` hotkey, which the kill switch records as `SourceHotkey`) and the plain request, as for the button (D-88).
- Verified: 19 scenarios of fed events with exact times (three quick, at the limit of 1200 ms, one millisecond too slow, sliding, two only, four quick, a held key, one taken by the dialog, an IME composition, an untrusted event, shift, alt and meta, another key, the combination, Ctrl+Esc, Ctrl+Shift+Alt+Esc, one taken, and a kill by the combination clearing the count) and the hints; in a real browser with real key presses: three Esc kill (with the hint after the first, and the source recorded as the hotkey), Ctrl+Shift+Esc kills, three Esc presses that answer three approval requests kill nothing and never reach the window, and the kill button's tooltip names both ways. ## D-93 — The viewer window, its whole process tree, and the dead-man switch (P6-T08)
- Status: Accepted (2026-10-18) · Type: Interpretation (fills in PLAN §10.4, §11 "Dead-man switch" and D-20), with one correction found by running a real browser
- Context: the viewer must open without the person doing anything, must go away with the session, and the agent must not keep acting when nobody can see it. A real browser showed that "kill the process we started" is not enough: Edge's first process starts the real browser and **exits**, so the process we hold is gone while the window, a different tree, stays open and keeps its profile locked (Chrome keeps its first process, which hid this).
- Decision (`internal/viewer`: `launcher.go`, `proc_unix.go`, `proc_windows.go`, `deadman.go`; `Hub` ping settings):
  1. **Modes** (`viewer.mode`): `window` (a window of its own), `browser` (the default browser), `none` (nothing), `webview` (not built; PLAN Phase 9: it falls back to `window` and the notice says so). The address given must be `http://127.0.0.1:<port>/…` with no user, no space, quote or line break: it goes on a command line, and nothing else is ever opened.
  2. **The window**: the first of Edge, Chrome, Chromium and Brave found (Program Files, Program Files (x86) and the user's local folder on Windows; `/Applications/…` on macOS, also under the home folder; names on `PATH` on Linux), started as PLAN §10.4 says: `--app=<login link> --user-data-dir=<session>/viewer-profile --no-first-run --no-default-browser-check --disable-extensions --disable-sync --window-size=1440,900`. The profile is private to the session (mode 0700) and removed with the window. It never adds `--no-sandbox`.
  3. **Falling back, never failing the session over the window**: no such browser, a profile that cannot be made, or a browser that cannot be started, and the default browser is tried (`open`, `xdg-open`, or `rundll32 url.dll,FileProtocolHandler`; no shell); if that fails too the person is told the address to open themselves. `Window.Notice` is the sentence for the terminal (and the viewer's notices), `Fallback` says it happened. (The plan names `pkg/browser`; the three commands are all it does, and no dependency was added.)
  4. **The whole tree.** The browser is started in a **job object** on Windows (created suspended and put in the job before it runs, so nothing it starts can be outside; the job kills what is in it when closed, so the window does not outlive a crashed controller) and in its own **process group** on Unix. `Kill` ends everything in it; `Closed` closes when nothing of the tree is left (polled every 250 ms), which is when the person closes the window, not when the first process exits. `Window.Kill` then removes the profile, retrying for 2 s because a browser holds its files for a moment. It is the teardown step the kill switch calls (`Killer.AddHook`).
  5. **Dead-man switch** (`Deadman`, following the connection, not a heartbeat in the page: a hidden or covered window has its timers throttled by the browser, but still answers the host's pings, so a window behind other windows does not end a session). Connected → nothing runs. Gone for **3 s** → `Pause()` (a reload does not pause anything); the agent **stays paused** if the viewer returns: only the person's Resume resumes it. Gone for **60 s** → `End()` (`KillOnExpiry` fires the kill switch with source `deadman`). `Arm()` starts the clock for a window that never opens. Each absence is numbered, so a timer of an earlier one that was already firing when it was stopped does nothing in a later one. `Stop()` ends the watch.
  6. **How a vanished window is found**: a window that closes or crashes closes its socket at once; one that vanishes without closing (sleep, network) is found by the hub's ping, now every 5 s with 5 s to answer (`HubOptions.PingEvery`, `PingTimeout`), so within about ten seconds.
  7. **Tooling that this task needed** (amends D-92): `go run ./tools/dev mutate` now runs the tests once **without** the change and refuses to go on if they fail (a test file with a syntax error is a "setup failed" that had made every change look caught), and counts as caught only a failed test or a crash, never a failure it does not recognize (those are `INVALID`).

## D-94 — The session's state machine, and how the rest of the session is built (P7-T01)
- Status: Accepted (2026-10-18) · Type: Interpretation (fills in PLAN §3.4 and §11)
- Context: every part of the session (the turn loop, the viewer, the audit log, the dead-man switch, the kill switch) has to agree on what state the session is in, and a few events race: the person pauses at the moment the task ends; a confirmation expires at the moment the viewer goes; the kill arrives in the middle of a move. PLAN §3.4 draws the states; the code must make a wrong move impossible, not merely unlikely.
- Decision (`internal/session/state.go`):
  1. **Ten states** with the viewer's names: `booting`, `handshake`, `ready`, `running`, `awaiting_confirm`, `awaiting_user`, `paused`, `ending`, `ended`, `killed`. `Terminal` (ended, killed), `Final` (ending too) and `Active` (a task is in progress, moving or not) say what a caller needs to know.
  2. **The diagram is a table, and the table is the only way a state changes.** `Booting → Handshake → Ready ⇄ Running ⇄ {AwaitingConfirm, AwaitingUser, Paused}`; `Running`, `AwaitingConfirm`, `AwaitingUser` and `Paused` can go back to `Ready` (done, Stop, the task's budget); every state but the two terminal ones can go to `Ending` and to `Killed`; `Ending` goes to `Ended` or `Killed`; nothing leaves `Ended` or `Killed`. Notable things the table refuses: a task before the agent has answered, a pause or a question with no task, a session that comes back from `Ending`. A move that is not in the table is a `TransitionError` and changes nothing.
  3. **`To` and `ToIf`.** `To(next, reason)` is for the move the caller is sure of (the error is a bug). `ToIf(from, next, reason)` moves only if the session is in one of the states `from`, and says whether it did: it is how two events that race are answered without one undoing the other (`ToIf({Running}, Paused)`: a pause that arrives at the moment the task ends does nothing, instead of pausing a task that is over).
  4. **Observers** (`OnChange`) hear every move, one at a time, **in the order the moves were made** (a lock is held while they are told, so a viewer cannot be told `paused` after `running` it came before), with the old and new state, the reason and the time. An observer must not make a move itself.
  5. **Two gates.** `WaitRunning(ctx)` is the gate of the turn loop: it waits while the session is paused, awaiting the person, or not yet ready, returns `Running` when it is, and returns what it found when the task ends (`Ready`) or the session does, so a loop never waits for a task that is over. `Wait(ctx, states…)` waits for a state, and says (`ErrFinal`) when the session ended without reaching it.
- How the rest of the session is built (the plan for P7-T02 to T07, amended by the entries that build each part): the session is a set of small units with narrow interfaces, each tested with fakes before it meets the others: the **executor** (an LLM action to agent requests and a result), the **dispatcher** (for each action: killed? → coordinates to the guest's → policy → profile → confirmation → rate limit → plan to the viewer → execute → audit and trace; the policy always sees guest coordinates and the audit keeps both the model's and the guest's), the **turn loop** (§11: gate, budget, observe, ask the model, parse and repair, dispatch the batch, loop detection), the **Inbound** the hub calls (chat, confirmations, controls), the **guards** (budgets, loop detector, circuit breaker, dead-man), the **fallback** (QMP when the agent is down) and the **runner** that wires them to the real VM, the viewer, the audit log and the kill switch. The state machine is what they share.
- Verified: the transition table is checked pair by pair (all 100) against a second, separately written copy of the diagram; the shape the plan describes (every non-terminal state can be killed and can end; nothing leaves a terminal state; a task starts only from Ready; the VM is unusable before the handshake); the names against the viewer's constants; error messages; observers heard in order with reasons and times; 4 goroutines making 3,200 racing moves (every change heard begins where the one before ended); `ToIf` with states asked for and not; the gates (paused, awaiting each, booting, a task that ends, a session that ends, a canceled context); `Wait`. Race detector clean on real Linux (3 runs). 16 of 16 mutations caught (the table's edges, unknown states, disallowed moves, observers, `ToIf`'s states, the initial state, each state of the gate, the announcement to waiters, the reason).

## D-95 — The executor and the dispatcher: what an action goes through between the model's mouth and the guest (P7-T02, first half)
- Status: Accepted (2026-10-18) · Type: Interpretation, with two deviations from PLAN §11 and §12 that make it stricter (below)
- Context: the model's actions are the only way anything in the guest changes. Everything that makes them safe (the rules, the person's say, the budgets, the record) has to happen in one place and in one order, or each caller will do it a little differently. The turn loop (the second half of this task) must not know any of it: it hands over an action and gets back what to tell the model and whether to go on.
- Decision (`internal/session/exec.go`, `dispatch.go`):
  1. **The executor** turns one validated action, already in guest pixels, into the agent's requests and a `prompt.Result`. It is the only code that knows the agent's protocol for actions. It keeps the last view of the screen (`SetView`: the raw tree, text and screen info the observer read), so that ids (`a…` tree elements, `o…` lines of text, `w…` page elements) mean the same thing to the policy and to the executor. Every wait has a margin over what the guest is asked to spend (`callMargin`, 15 s): the guest's own timeout speaks first and says why. What the guest says in an error is cleaned like any text from the guest before it reaches the model (it cannot forge a fence or a message). `done` and `ask_user` are the loop's, not the executor's.
  2. **The dispatcher** runs one action through a fixed pipeline: killed? → the model's coordinates to the guest's (`Mapper.Guest`; a coordinate outside the picture is the model's to correct, `invalid_args`) → the rules judge it **on guest coordinates** (exec by command, GUI by the tree the model last saw) → the profile turns the verdict into what is enforced (`--step` asks for everything, `--unsafe` turns asking into doing and refusing into asking) → a refusal ends there → a confirmation waits for the person (the state is `awaiting_confirm` meanwhile; a kill or Stop that comes while the question is open wins over an approval that comes with it) → the rate limit and the budgets admit it (charged only when admitted: a refused or unapproved action costs nothing) → **the decision is written to the audit log** → the viewer is told the plan and that it runs → the executor does it → **the result is written** → the viewer is told how it ended.
  3. **Deviation 1: the decision is on record before the action runs** (PLAN §11 wrote one record after). An action that is started and never finishes (the host dies, the guest hangs, the power goes) still shows in the log, with what it was, why, and under which rules. Each executed action therefore has two records, `decision` and `result`, with the same action id; a refused one has the decision alone. If the decision cannot be written, the action is **not run** and the session ends (`StopAudit`): a log that cannot be written is a log that cannot be trusted, and the thing it would have recorded is not allowed to happen unrecorded. If the result cannot be written the action did run, and the session ends all the same.
  4. **Deviation 2: the log keeps the model's own arguments, the policy sees the guest's.** The `decision` record carries the arguments as the model wrote them (in its picture's pixels) so that the record can be read next to the transcript; the policy and the executor are never given those numbers. The viewer's plan carries the guest's coordinates, since it draws on the guest's screen.
  5. **What must not be shown is not shown.** Text typed or set into a password field (the rule says so: `redact_text`) is masked to its length and a short hash; secrets the session knows (the API key, if any) are removed by the redactor; both before the arguments reach the log, the viewer's trace or the confirmation dialog. The guest receives the real text.
  6. **Why the loop stops where it does** (`Step.Stop`): a refusal, an unapproved action, a failure or a rate limit ends the batch (`StopBatch`: the model is told and plans again; the rest of its actions were planned for a screen that no longer exists); a kill (`StopKilled`), Stop or a canceled context (`StopCanceled`), the session's time (`StopTimeout`) and a dead audit log (`StopAudit`) end the response and are the loop's to act on; the task's budget (`StopBudget`) pauses for a check-in. A response's own allowance (`ActionsPerResponse`, already applied when the loop cuts the response) ends the batch but not the task.
  7. **Verdict words in the log** are a closed set: `allowed`, `confirmed`, `denied`, `rejected`, `confirm_timeout`, `no_viewer`, `confirm_failed`, `canceled`, `rate_limited`, `session_timeout`, `budget`, `invalid`, `killed`.
- Also: `vision.Seen` now carries `Raw` (the agent's own answers, in guest pixels) next to the converted ones, because the part of the session that acts on them judges and aims in the guest's terms.
- Verified: the executor against a fake agent: every tool's request (27 mutations caught), including the deadline margins, which were first asserted loosely and let a mutation through on a coarse clock. The dispatcher with the real rules, the real broker and the real limits, and fakes for the guest, the log and the viewer: the order of the pipeline (what the log held at the moment the command ran), every verdict and its stop, the person's note cleaned on approval and rejection, the state while waiting, a kill during the question, a canceled wait that gives its charge back, a dead log before and after the action, a password never in the log, the viewer or the dialog (and in the guest), and each kind of GUI action judged by its own rules (drag from and onto, shift+Delete, the focused password field, a page address that is code, a password box by selector and by id). About 70 mutations caught in `dispatch.go`; the survivors were three missing assertions (the early cancel check, the profile on GUI actions, a failed presenter), now tests. Race detector clean on real Linux.

## D-96 — The turn loop: what pauses a task, what ends it, and what ends an answer early (P7-T02, second half)
- Status: Accepted (2026-10-18) · Type: Interpretation (fills in PLAN §11); amends D-95 on who writes the advice to the model
- Context: PLAN §11 gives the loop in ten lines of pseudocode. Everything that makes a loop safe to leave alone for an hour is in the cases the pseudocode does not list: a model that answers in prose, a screen that cannot be read, a Stop that arrives while a question is open, a budget that runs out in the middle of an answer. Each needs one rule that holds everywhere.
- Decision (`internal/session/loop.go`, `loop_batch.go`):
  1. **The loop knows four things, each behind a small interface**: it looks (`Looker`, the `vision.Observer`), it acts (`Actor`, the dispatcher of D-95), it talks to the person (`Person`: the messages they wrote, and a question that waits for an answer) and it is watched by a `Guard` (the same action again with the screen unchanged; too many failures in a row). The session wires the real ones in P7-T06; the loop is tested with fakes for the screen, the model, the actor, the person and the guard, and with the real state machine, budgets and conversation. One test runs it over the real dispatcher, rules, confirmations and executor.
  2. **A task ends in one of seven ways** (`Outcome.End`): `done` (the model said so; `Success` is its own verdict), `stopped` (Stop, or the context ended), `killed`, `timeout` (the session's time), `audit_failure`, `failed` (something that will not mend by itself) and `session_over` (the session went away under the task). When the session goes on, a task that is done, stopped or failed leaves it `Ready`; for the other four the state is the runner's.
  3. **What pauses, and what ends.** *A failure that can mend pauses the task and says so; the person resumes it (and the turn is made again from the top, with a fresh look at the screen) or stops it*: a screen that could not be read, a model that did not answer (unreachable, rate limited, server error), three unusable answers in a row (the first plus `parse.MaxRepairs` repairs), the guard's word, and a budget check-in. *A failure that will not mend ends it*: a model that refuses the key, the request or the model's name (auth, bad request, not found), a conversation that cannot fit the model's context even with everything optional cut (the person is told how to fix it), a dead audit log, a kill, the session's time. Nothing pauses by itself and resumes by itself: a pause waits for a person.
  4. **Every native call is answered**, whatever became of it: the APIs refuse a conversation with an unanswered call. A call that was not valid is answered with what was wrong, one that was valid but came after an invalid one with "not run", one beyond the limit with "dropped", one that the batch ended before with "not run" and why. This holds when the task is stopped in the middle of an answer (the next task starts from a conversation that is still well formed) and when nothing in the answer could be run (the model is then asked to answer again, up to the repair limit). An answer without native calls (JSON mode, or a native model that wrote its actions as text) has its results in the next observation instead, and what was wrong with its actions in a note.
  5. **The batching rules** (§11): the actions of an answer run one by one, and the rest are not run when an action was refused or did not work; when it was `done`, `ask_user` or `screenshot` (the next observation shows the screen); when the task was paused, stopped or killed meanwhile (the gate is checked before every action, and an answer that waited through a pause is dropped: the screen may have changed); when the response's own allowance is spent; and **when the screen changed since the model looked and the next action says where to click** (`mouse`, `scroll`). The comparison is of the agent's screen hashes: the one at the picture the model saw against the hash after each input. Without a picture (text-only) the first hash after an input is the baseline: a change cannot be told from nothing. An action that names an element by id is not held back by a changed screen: the agent checks the id's generation itself and answers `stale_element`.
  6. **`done` and `ask_user` are the loop's own.** They are not given to the dispatcher (no rule has anything to say about them, they cost no budget and `--step` does not ask about them) but are recorded like any action: an `action` record with verdict `allowed` and the result, a trace for the viewer, the picture's hash. `done` ends the task with the model's verdict and summary (shown in the chat). `ask_user` puts the session in `awaiting_user`, shows the question, and waits for the person; the answer goes back as the result (up to 300 characters; a longer one is also put in the next observation, under the person's own words). A question that cannot be put because the context ended is a Stop; one that cannot be put for any other reason is told to the model as a failure.
  7. **The model's calls are recorded without the model's words**: an `llm` record per answer with the model's name, tokens, latency, whether it was cut off, the number of tool calls and the SHA-256 of the text, never the text (it can hold what was on the screen). The model's thought (what it says beside its actions) goes to the viewer's conversation.
  8. **The advice is `prompt.Hint`, and only there** (amends D-95): the dispatcher keeps the facts ("Refused by the safety rules: DENY-ROOT-WIPE (…)", "The user rejected this action. The user wrote: …") and adds the one sentence about what to do instead through `Hint(code)` once, for every failed result. The viewer is shown the facts without the advice. Sentences are joined without doubled stops.
  9. **A budget check-in is a pause**: a spent allowance of turns (before the turn) or of actions (after the answer that spent it, so that the model is not asked for actions that will all be refused) pauses the task; resuming gives another full allowance and forgets what the guard had seen.

## D-97 — The console: what the person does in the page, and where it goes (P7-T03)
- Status: Accepted (2026-10-18) · Type: Interpretation (fills in PLAN §11, §6.7 and §10.2)
- Context: the page has a chat box, an Approve/Reject dialog and the buttons Pause, Resume, Stop, Step and Kill. Three parts of the session want to hear of them in three different shapes: the hub calls an `Inbound`, the confirmation broker shows its questions through a `Presenter`, and the turn loop asks for a `Person`. The same state (the queue of what was written, the question that waits for an answer, the task that Stop cancels) is behind all three, so one object serves them.
- Decision (`internal/session/console.go`; `Dispatcher.SetStep` in `dispatch.go`):
  1. **One `Console`**, whose methods never block (the hub calls them from the goroutine that reads the connection). It is `viewer.Inbound` (`Chat`, `Confirm`, `Control`), `confirm.Presenter` (`Present`, `Resolved`) and `Person` (`Messages`, `Ask`).
  2. **What the person writes** is cleaned and cut (2,000 characters), shown back to them as a chat line **from the session** (so the page's list is the session's record, not the page's own), written to the audit log (`user`/`chat`, with the text masked by the session's redactor), and then goes where it is meant for, in this order: *the answer to the model's question*, if one is waiting; *the start of a task*, if the session is `Ready` (the runner's `StartTask` takes the text; it must not block); otherwise it is *kept for the model's next observation*, as a message from the person (trusted; the newest 20 are kept). A message to a session that is ending is dropped.
  3. **Every word from the person counts as activity** (chat, an answer, a button): it postpones the idle timeout.
  4. **Answers to confirmations** go to the broker; an id the broker does not know (a page open since the question ended) is ignored and not logged. The note is cleaned; the answer is logged (`user`/`confirm`: the id, the decision, the note). The question is put to the page only while a page is attached: `Connected` gives the broker the console as its presenter, `Disconnected` takes it away, which refuses every open question (`no_viewer`: nothing can be approved when nobody is looking). The outcomes the page is told are `approved`, `rejected`, `expired` (timeout) and `canceled` (no viewer, Stop, failure to show).
  5. **Controls.** *Pause* moves `Running` to `Paused` and nothing else (a question the model asked, or one about an action, is answered, not paused over). *Resume* moves `Paused` to `Running`, and so also answers a budget check-in. *Stop* cancels the task's context, which ends the model call, the action, the wait for an answer and the pause alike, and cancels the open questions; the loop then leaves the session `Ready`. Stop with no task running does nothing but cancel open questions. *Step on/off* switches step mode in the dispatcher while the session runs (`Dispatcher.SetStep`: 1 on, 2 off, 0 leaves it to the profile); the person's word wins over `--step` in both directions, and the viewer is told with a notice. *Kill* never comes here (the hub fires the kill switch). Every control is logged (`user`/`control`).
  6. **A task's context** comes from `Console.Begin(parent)`: the runner runs each task in it, and Stop cancels it.
  7. **The audit log failing while the person does something is as fatal as anywhere**: `Fatal` is called (the runner connects it to the kill switch).
  8. `Attach` makes the viewer hear of every change of state, with its reason, in the order the moves were made (an observer of the state machine, D-94).
- Verified: 24 tests (and a table of four step combinations): the order messages go to (answer, task, kept), what is dropped, the cleaning and the mask, the bound, the idle timeout, a confirmation put to the page and answered through the real broker (including a stale id), every outcome in the page's word, the page leaving with a question open, each control in each state it should and should not work in, Stop reaching the task, the open question and the wait for an answer, step mode through the real dispatcher on all four combinations of profile and word, and the console under the real loop (a question answered in the chat, a message in the middle of a task reaching the next turn, Pause holding the actions, Stop from the page). 50 mutations of the console and the step switch caught; the survivors were an equivalent mutant (a pause over a question, which the state table already refuses), two weak assertions (the page's timestamps and notices) and some code that did nothing (the clearing at the end of a task), now removed. Race detector clean on real Linux.

## D-98 — Guards, the watchdog and the dead-man switch: when a session stops trusting itself (P7-T04)
- Status: Accepted (2026-10-18) · Type: Interpretation (fills in PLAN §6.6 and §11)
- Context: the budgets of D-96 stop a task that does too much. Three other things go wrong without going over any budget: a model that does the same thing again and again, a model whose every action fails, and a person who is no longer there (the window closed, the laptop shut, the machine asleep). None of them is a reason to throw the work away; all of them are reasons to stop spending the person's time and money without anyone looking.
- Decision (`internal/session/guards.go`):
  1. **`Guards`** is the loop's `Guard` (D-96) over the `limits.LoopDetector` and `limits.Breaker` that the safety layer already had. *A repeat* is the same tool with the same arguments (the order of the model's keys does not matter) **and** the same state, three times in a row. The state is the hash the agent gave of the screen after an input, and for what gives none (exec, reading the tree, a click on an element) a fingerprint of what the model saw that turn and of what came back (the success, the code, every stream of text). So `ls` three times with the same output on the same screen is a loop, `date` three times is not, and a click on "Next" that turns the page is not either. In text-only mode what the model saw is a hash of the tree and the screen text. *The breaker* counts actions that failed and answers that could not be used, five in a row; a success clears the count, a usable answer does not (its action may be the next failure). Each says what happened in words for the person; both are cleared by Resume.
  2. **The guard sees every action that ran, the failed ones too.** The first version asked it only about the ones that went well, so the breaker could never trip; the test of the breaker under the loop found it.
  3. **`Watchdog`** watches the two clocks that no task is there to watch: the session's whole allowance of time (a task that waits for the person for hours does not notice it running out) and the idle timeout, which counts only while the session is `Ready` or `Paused` (a task that is running is not idle; the console postpones it with every word of the person's, D-97). It looks once at the start and then every second, calls `OnExpire` once with the clock that ran out, and stops with the session or its context.
  4. **`NewDeadman`** is the dead-man switch of D-20 over the viewer's: after 3 s without the viewer the task is paused (`Console.PauseFor`: `Running` to `Paused` and no other move), and **a viewer that comes back does not resume it**: only the person's Resume does; after 60 s the session ends. A reload inside 3 s pauses nothing.
- Not here: the budgets themselves (D-96's check-ins), the counters in the viewer's header (the pump's figures, P7-T06), and what the runner does when `OnExpire` or the dead-man's `End` fires (it ends the session in order; P7-T06).
- Verified: 22 tests; the repeat and the breaker at their thresholds and just under them, what makes two states different (one by one: the hash, the screen, the success, the code, the stream, the text), the reset, the defaults in the words too, the guard under the real loop (a model that repeats itself pauses the task and a varied one does not; five failures pause it; what failed is still told to the model), the fingerprint of what the model saw, the watchdog with ticks and a fake clock (session time, idle in `Ready` and in `Paused` and not while running, once, stops with the session and the context), and the dead-man switch with fake timers (pause at 3 s, no auto-resume, a reload, the end at 60 s). 47 mutations caught; the invalid ones were redone. Race detector clean on real Linux.
